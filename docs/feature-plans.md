## 当前已实现状态

以下功能已在 `mobile.html` 中实现并提交（commit `46aa08d`）：

- **附件面板基础框架**：点汉堡按钮弹出面板，替换键盘位置，输入框位置不动

- **汉堡按钮**：CSS 绘制三横线图标，替代原来的"+"号，语义更准确（兼具"控制"和"附件"双重含义）

- **按钮显隐切换**：输入框为空时显示汉堡按钮，有内容时显示发送按钮，同一时间只显示一个

- **按钮颜色跟随模式**：汉堡按钮颜色与发送/自动按钮一致（手动模式绿色，自动模式橙色），帮助用户区分当前模式

- **发送按钮尺寸**：40×40px，与输入框平行，由整体布局控制

- **面板/键盘切换**：点汉堡按钮 → blur 输入框 → 键盘消失 → 显示面板；再点 → focus 输入框 → 键盘弹出 → 面板消失

- **面板高度同步**：使用公式 `panelHeight = cachedKeyboardHeight - currentKeyboardHeight` 实现面板高度跟随键盘反向变化，面板可见时整个页面固定不跳动

- **面板消失唯一途径**：聚焦输入框（触发键盘弹出，面板被替换）

## 整体界面架构

### 核心设计：底部固定 + 附件面板替换键盘

输入框始终在底部紧贴输入法（PhoneMic 靠手机输入法自带的语音识别，无独立麦克风按钮）。上方为聊天记录区域。点汉堡按钮时，附件面板替换键盘位置，输入框位置不动。

```
  正常状态（键盘弹出）：          点汉堡按钮后（面板弹出）：
┌──────────────┐              ┌──────────────┐
│  聊天记录     │              │  聊天记录     │
│              │              │              │
├──────────────┤              ├──────────────┤
│ [输入框]     │              │ [输入框]     │  ← 位置不动
├──────────────┤              ├──────────────┤
│  输入法键盘   │              │  附件面板     │  ← 高度=键盘高度
│  (320px)     │              │ (Tab│内容区)  │
└──────────────┘              └──────────────┘
```

**设计演进历程：**

最初考虑过"上下分区 + 顶部 Tab 切换聊天/控制"的方案，但讨论后发现：

1. 控制模式如果也放输入框，输入法弹出会严重挤压控制按钮空间
2. 如果控制模式不放输入框，用户要输入时需切回聊天模式，增加切换摩擦
3. 网页无法控制输入法的弹出/消失（OS 层面行为，浏览器 API 只能感知不能阻止）

最终采用**附件面板方案**（模仿微信"+"号行为）：控制按钮和文件传输功能放在附件面板中，面板替换键盘位置，输入框始终在底部固定不动。这样：

- 输入框永远紧贴输入法/面板，符合手机操作习惯

- 面板有充足空间排列按钮（高度等于键盘高度，一般 280-360px）

- 切换零摩擦：点按钮切换面板/键盘，输入框位置不变

- 聊天记录始终在后台更新，切回即看到最新内容

### 面板/键盘切换逻辑

```
状态A：键盘可见               状态B：面板可见
     ┌──────┐                    ┌──────┐
     │ 输入法 │                    │ 面板  │
     └──────┘                    └──────┘
          ↕ 点汉堡按钮              ↕ 点汉堡按钮
          ↘               ←────────/
              ↘          ←──────/
                  点输入框聚焦
```

- **键盘→面板**：点汉堡按钮 → `input.blur()` 收起键盘 → 显示同高度面板

- **面板→键盘**：再点汉堡按钮 → `input.focus()` 弹出键盘 → 面板消失

- **面板消失的唯一途径**：聚焦输入框（触发键盘弹出替换面板）

- **面板可见时**：整个页面固定不跳动（面板高度跟随键盘反向变化）

### 汉堡按钮设计

用 CSS 绘制三横线图标（汉堡图标），替代原来的"+"号：

- 语义更准确：兼具"控制面板"和"附件菜单"双重含义

- 颜色跟随发送/自动按钮（绿色=手动模式，橙色=自动模式），帮助用户区分当前模式

- 纯 CSS 绘制，无图片依赖，跨平台一致

### 按钮显隐切换

输入框为空时显示汉堡按钮，有内容时显示发送按钮：

```
输入框为空：               输入框有内容：
┌──────────┬──┐         ┌──────────┬──┐
│          │ ≡ │         │ 今天天气不错│发送│
└──────────┴──┘         └──────────┴──┘
  显示汉堡隐藏发送          显示发送隐藏汉堡
```

两个独立按钮，各自独立 handler，通过 `display` 切换显隐，代码干净不耦合。

### 鼠标 Tab 页（预设计）

切换到鼠标 Tab 后，整个面板区域变为触摸板，控制 PC 端鼠标。

```
┌──────────────────────────┐
│                          │
│    触摸板区域              │
│    （相对移动模式）         │
│                          │
│  手指滑动 → 鼠标移动       │
│  单指轻点 → 左键单击        │
│  双指轻点 → 右键单击        │
│                          │
└──────────────────────────┘
```

**核心设计：相对移动（非绝对定位）**

采用笔记本触摸板的相对移动模式，而非画板的绝对定位：

- 追踪手指移动的**增量**（dx, dy），不是手指的绝对位置

- 发给 PC 的是"鼠标向右移 N 像素"，不是"鼠标移到 (x, y)"

- 手指抬起 → 鼠标停住；手指再按下 → 从新位置继续移动

- 面板面积 ≈ 键盘高度（280-360px），与笔记本触摸板尺寸接近，配合"抬手重定位"够用

**手势设计**

| 手势      | 动作   |
| ------- | ---- |
| 单指滑动    | 鼠标移动 |
| 单指轻点    | 左键单击 |
| 单指双击    | 左键双击 |
| 单指按住+移动 | 拖拽   |
| 双指轻点    | 右键单击 |
| 双指上下滑   | 滚轮滚动 |

**技术要点**

- `touchstart`/`touchmove`/`touchend` 事件追踪手指移动增量

- `event.touches.length` 区分单指/双指手势

- CSS `touch-action: none` + `e.preventDefault()` 阻止浏览器默认手势干扰

- 轻点判定：`touchstart` 到 `touchend` 时间 < 200ms 且位移 < 10px

- 双击判定：两次轻点间隔 < 300ms

**关于"延伸到面板外"的讨论**

初始设想是手指从面板起步后可延伸到整个屏幕区域。技术上可行（`touchmove` 事件会继续派发给 `touchstart` 所在元素），但：

- 手指视觉上在聊天区域滑动，用户会困惑

- 需要在更大范围 `preventDefault`，影响范围大

- 相对移动 + 抬手重定位（真实触摸板交互方式）已经够用

**当前结论**：先做面板内相对移动，"延伸到面板外"作为后续增强再考虑。

**参考实现**：[remote-mouse](https://github.com/rust17/remote-mouse) 是纯网页实现的触摸板，架构与 PhoneMic 相同，可借鉴。

## 功能一：图片/文件传输

### 背景

微信可以传图片到电脑，但需要安装微信。如果 PhoneMic 内置这个功能，手机和电脑都能用，不依赖第三方软件。

### 入口

文件 Tab 页中的选项（见上方"文件 Tab 页"）。

### 传输协议

| 方案             | 效率     | 复杂度                       | 结论        |
| -------------- | ------ | ------------------------- | --------- |
| Base64 塞进 JSON | 膨胀 33% | 最低，复用现有 WebSocket JSON 协议 | **推荐**    |
| 二进制帧           | 无膨胀    | 需改 WebSocket 协议           | 传大量大文件才值得 |

PhoneMic 偶尔传一张图，base64 开销可忽略。复用现有 JSON 消息格式，加一个新 `type`。

### 手机端 UX

- `<input type="file" accept="image/*">` 文件选择器（选相册）

- `capture="environment"` 拍照

- `paste` 事件从剪贴板粘贴

- 入口在附件面板的文件 Tab 页中

### 电脑端 UX

| 方案           | 优点                | 缺点       |
| ------------ | ----------------- | -------- |
| 放剪贴板         | 用户自己 Ctrl+V 到任意位置 | 多一步手动粘贴  |
| 自动粘贴         | 无缝，像 AirDrop      | 可能粘到错误窗口 |
| 保存到文件夹       | 安全有备份             | 要去文件夹找   |
| **剪贴板 + 保存** | 即可粘贴又有备份          | 略复杂      |

**推荐方案：剪贴板 + 自动保存到临时目录**

- 图片到剪贴板，用户随手 Ctrl+V 到微信/文档/编辑器

- 同时存一份在 `%TEMP%/phonemic/` 兜底

- 不自动粘贴，因为用户切窗口时机不确定，粘到错误窗口会很尴尬

- 状态栏提示"图片已到剪贴板"

### 完整流程

```
手机端                          电脑端
  │                               │
  │  文件Tab→"发送图片"选图         │
  │  ↓                            │
  │  JS 读 File → base64           │
  │  ↓                            │
  │  WS 发送 JSON {type:"image",  │
  │    data:"base64..."}          │
  │ ─────────────────────────────→│
  │                               │  解码 base64 → bytes
  │                               │  写入剪贴板（CF_DIB）
  │                               │  同时存到 %TEMP%/phonemic/
  │                               │  状态栏提示"图片已到剪贴板"
  │  WS 回传 {type:"image_ack",  │
  │    status:"ok"}               │
  │ ←─────────────────────────────│  手机端聊天记录显示"已送达"
  │                               │  用户 Ctrl+V 粘贴
```

### Windows 剪贴板放图片

```python
import io
from PIL import Image
import win32clipboard

def image_to_clipboard(image_bytes):
    img = Image.open(io.BytesIO(image_bytes))
    output = io.BytesIO()
    img.save(output, "BMP")
    data = output.getvalue()[14:]  # 跳过 BMP 文件头 14 字节

    win32clipboard.OpenClipboard()
    win32clipboard.EmptyClipboard()
    win32clipboard.SetClipboardData(win32clipboard.CF_DIB, data)
    win32clipboard.CloseClipboard()
```

### 文件传输（非图片）

图片以外的文件（PDF、docx 等）不能放剪贴板，只能保存到文件夹。默认存到 `Downloads/PhoneMic/`，状态栏提示文件路径。

### 聊天记录富内容显示

发送图片/文件后，聊天记录里也显示对应条目：

```
┌─ 聊天记录 ──────────────┐
│  你: 今天天气不错        │  ← 文本消息
│  PC: 已输入              │
│  你: [图片缩略图] 2.3MB  │  ← 图片消息
│  PC: 已到剪贴板          │
│  你: report.pdf 500KB   │  ← 文件消息
│  PC: 已保存到 Downloads  │
└──────────────────────────┘
```

### 长按/短按逻辑变化

现有逻辑：短按=复制到剪贴板，长按=直接输入。加入图片/文件后需要调整：

| 操作 | 文本消息       | 图片消息   | 文件消息  |
| -- | ---------- | ------ | ----- |
| 短按 | 复制到剪贴板（现有） | 重新放剪贴板 | 待定    |
| 长按 | 直接输入（现有）   | 打开预览   | 打开文件夹 |

> 待思考：图片和文件在聊天记录里点击的行为还需确认

2. 多图：支持一次选多张批量传，还是一张一张传

## 功能二：快捷按钮与 PC 端自定义功能

### 背景

语音输入是 PhoneMic 的核心，但有些操作"出声不方便"（开会时按静音）或"语音太慢"（翻页说"下一页"不如直接按 PgDn）。需要一个快捷按钮面板补足这些场景。

### 定位

**语音是主力，按钮是补充**。不是"替代键盘"，而是补足语音不方便的场景：

- 开会时不能出声 → 按一下"静音"

- 翻页时说"下一页"太慢 → 直接按 PgDn

- 需要精确快捷键（Ctrl+Shift+Esc）→ 语音识别不稳定，按钮确定性高

### 核心思路：复用现有命令系统

PhoneMic 已有完整的命令系统（`commands_manager.py`），用户已能创建"匹配文本 → 执行动作"的命令。只是现在只能**语音触发**。

给每条命令加属性 `"showButton": true`，在附件面板控制 Tab 页中把这些命令渲染成按钮，一点就执行——不需要新建一套自定义系统。

```
现有：用户说"回车" → 匹配命令 → send_keys("{ENTER}")
新增：用户点"回车"按钮 → 直接执行同一条命令 → send_keys("{ENTER}")
```

### 为什么不在手机上做编辑

手机上做"创建快捷按钮"的编辑器会很痛苦——小屏幕、虚拟键盘、输入快捷键符号都很难。让用户在 PC 端的设置界面配好，手机端只负责"展示和点击"。

### PC 端自定义功能设计（待定）

**确定的方向：**

- 自定义功能必须放在 PC 端，不在网页端做编辑

- 复用现有命令系统，给命令加 `showButton` 属性

- 手机端只展示和点击，不提供编辑能力

**待设计的问题：**

1. **PC 端配置界面形态**：是在现有设置页面中加一个"显示为按钮"勾选框？还是做一个独立的按钮管理界面（拖拽排序、分组等）？
2. **按钮排序**：用户能否自定义按钮排列顺序？还是按创建时间/字母序自动排列？
3. **按钮分组**：随着按钮增多，是否需要分组或分页？还是控制 Tab 页只放最常用的几个（比如 9-12 个）？
4. **默认预设**：出厂带哪些按钮？建议覆盖最常见的无声操作场景（回车、删除、PgUp/PgDn、Esc、Tab、Ctrl+Z）
5. **图标/文字**：按钮上显示文字（如"回车"）还是图标？文字更直观但占空间，图标更紧凑但有认知成本

> 这个功能怎么设计好，还是一个问题，需要时间思考。当前方向明确（PC 端配置 + 手机端展示），具体 UX 待定。

### 与"空鼠标/键盘"方案的对比

| 方案            | 复杂度 | 实用性              |
| ------------- | --- | ---------------- |
| 完整虚拟键盘（全键盘布局） | 高   | 手机上打字不如直接语音      |
| 触摸板鼠标         | 高   | 手机屏幕太小不好操作       |
| **精选快捷按钮**    | 低   | 正好补足语音做不到的"无声操作" |

## 技术选型

### UI 框架：继续裸 div+CSS+JS，不引入框架

| 对比   | 裸 JS       | 引入框架（React/Vue） |
| ---- | ---------- | --------------- |
| 部署   | 一个 html 文件 | 要 build 或引 CDN  |
| 加载速度 | 零依赖        | 多 30-150KB      |
| 维护   | 一个文件改完     | 工具链、依赖管理        |

这些功能用 vanilla 写约 500-800 行 JS，加框架反而增加负担。等以后真的觉得维护不动了再引入不迟。

### 网页 vs 原生 App 的取舍

| 能力                     | 原生 App | 网页      |
| ---------------------- | ------ | ------- |
| 键盘附件视图（inputAccessory） | ✅      | ❌       |
| 后台录音/语音识别              | ✅      | 容易被系统杀掉 |
| 系统级快捷指令 / Widget       | ✅      | ❌       |
| 推送通知                   | ✅      | 有限支持    |
| 启动速度                   | ✅ 秒开   | ❌ 要加载页面 |
| 文件访问权限                 | ✅ 完整   | ❌ 受限    |
| 性能和动画                  | ✅ 流畅   | ❌ 有延迟感  |

但网页版的优势也是 App 比不了的：

| 优势       | 网页 | 原生                  |
| -------- | -- | ------------------- |
| 扫码即用，零安装 | ✅  | ❌ 要下载 App           |
| 全平台通用    | ✅  | ❌ 要分 iOS/Android 开发 |
| 维护成本     | 低  | 高（两个代码库）            |
| 不需要上架审核  | ✅  | ❌ App Store 审核麻烦    |

**核心判断**：PhoneMic 最大的卖点是"扫码即用，不用装 App"。如果让用户去装 App，就和市面上一堆"手机当鼠标"的软件没区别了，竞争优势就没了。网页版的限制是 PhoneMic 必须接受的 trade-off，在网页能做的范围内尽量做好，网页做不到的就不硬做。

### 网页键盘附件面板的实现限制

微信点"+"号时，输入法位置被替换成功能面板，输入框位置不动（iOS `inputAccessoryView` 效果）。网页版无法完全复现此行为：

| 平台           | 支持情况                                |
| ------------ | ----------------------------------- |
| iOS 原生       | ✅ `inputAccessoryView` 是系统 API      |
| Android 原生   | ❌ 无同名 API，但可用 `WindowInsets` 实现同等效果 |
| React Native | ✅ 有第三方库封装双端差异                       |
| 网页           | ❌ 完全做不到，浏览器不暴露此 API                 |

**已实现的网页近似方案**：记录键盘高度，点汉堡按钮时用同高度的面板替换键盘位置。面板可见时整个页面固定不跳动。实际使用中有轻微闪烁（键盘收起动画期间），属网页平台的已知限制，用户已接受当前程度。

### 已知问题与待优化

**iOS：面板切键盘时输入框下沉（明显跳动）**

- 现象：面板切键盘时，输入框先"跳下去"（向屏幕底部方向移动），然后才被键盘顶上来。跳动幅度较大，明显可见。
- 平台：仅 iOS 出现（测试机 iPhone 7），Android 微信浏览器无此问题。
- 初步分析：可能与 iOS 键盘弹出动画过程中 `visualViewport.resize` 连续触发、`cachedKeyboardHeight` 被持续覆盖有关。面板可见时冻结 cached 的修复方案实测无效，原因待进一步排查。
- 当前状态：问题已记录，暂不修复，待进一步观察和思考。

**Android 多浏览器兼容性**

- 现象：不同 Android 浏览器表现不一致
  - 微信浏览器：完美，无闪烁
  - 小米系统自带浏览器：面板无法弹出
  - 其他部分浏览器：快速切换多次后面板消失，只剩输入框
- 初步分析：可能与浏览器内核对 `visualViewport` API、`interactive-widget` 等特性的支持差异有关，待通过 UA 日志确认各浏览器内核信息后进一步排查。
- 当前状态：排查中。

## 总结

核心设计决策（按确定程度排列）：

1. **附件面板替换键盘**：点汉堡按钮弹出面板替换键盘位置，输入框始终在底部固定不动（已实现）
2. **面板/键盘切换**：点汉堡按钮切换面板和键盘，面板消失的唯一途径是聚焦输入框（已实现）
3. **面板高度同步**：面板高度跟随键盘反向变化，面板可见时整个页面固定不跳动（已实现）
4. **汉堡按钮**：CSS 绘制三横线图标，颜色跟随发送/自动模式（已实现）
5. **按钮显隐切换**：输入框空时显示汉堡按钮，有内容时显示发送按钮（已实现）
6. **两栏面板布局**：左侧窄 Tab 栏（控制/文件/鼠标），右侧内容区（待实现）
7. **控制 Tab 页**：常用键盘快捷按钮，复用命令系统（待实现）
8. **文件 Tab 页**：发送文件、图片、图片到剪贴板（待实现）
9. **鼠标 Tab 页**：面板变触摸板，相对移动模式，支持单指/双指手势（预设计）
10. **PC 端自定义功能**：用户在 PC 端配置快捷按钮，手机端只展示和点击（待设计）
11. **不引入 UI 框架**：继续裸 div+CSS+JS
12. **接受网页版限制**：不做 App，扫码即用是核心竞争力
