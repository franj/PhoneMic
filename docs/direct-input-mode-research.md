# 直接输入模式（动态文字上屏）调研总结

> 调研日期：2026-08-25  
> 状态：**已实现**（2026-09-13，方案 A）。下方保留原调研过程，实现与本文件有
> 偏差的地方以代码为准，偏差见文末「落地实现」。

## 背景

当前 PhoneMic 的文字输入流程：

1. 手机端每次输入都发 `preview` 事件，电脑端只在**悬浮窗**里显示文字
2. 语音识别结束、手机发 `send` 事件时，通过**剪贴板粘贴**（Ctrl+V）一次性上屏

**设想的新模式**：preview 阶段的文字直接打进目标输入框，识别过程中动态更新——像输入法一样逐字出现在光标位置。与悬浮窗模式二选一，用户自选。

## 方案评估

### 方案 A：键盘模拟 + diff 计算（已采纳，后搁置）

**原理**：用 `SendInput` 模拟键盘逐字打字，文字变化时做 diff（找公共前缀，只删差异部分、只打新增部分），send 时删掉所有 preview 文字再一次性粘贴最终结果。

**优点**：
- 不需要注入目标程序，不触发杀毒
- 不区分输入框类型（`SendInput` 是 OS 层面键盘模拟，对所有控件通用）
- 最终粘贴是原子操作，Ctrl+Z 一次撤销整段

**缺点**：
- send 时有"删-贴"的瞬间闪烁（<50ms，基本无感但理论存在）
- preview 期间用户不能切窗口/输入框，否则文字打错位置
- 需要检测焦点变化来回退

### 方案 B：剪贴板方式做 preview 更新（未采用）

每次 preview 更新 = 选中上一次打的字 + 粘贴新内容。每次更新是原子的，撤销干净。但精确选中"自己打的字"不碰用户原有文字很难，且自绘控件对 Shift+方向键选区行为不一致。复杂度高，放弃。

### 方案 C：TSF 输入法（理想方案，不合适）

**原理**：注册成 Windows TSF Text Service Provider（输入法），用 composition 机制管理动态文字，提交时原子化，撤销完美。

**结论：技术上完美，但产品上不合适。**

- TSF 的 composition 机制只有被系统激活的输入法才能用，普通程序无法操作
- 注册成输入法 = COM DLL 被系统加载进目标进程（系统官方注入，不会被判病毒）
- **但用户体验变了**：用户需要 Win+Space 切到 PhoneMic 输入法，用完切回去；切过去后电脑键盘也被 PhoneMic IME 拦截，不能互不干扰
- 跟产品"扫码即用、轻量无感"的定位矛盾

## 方案 A 技术细节（日后重启用）

### 状态机

```
IDLE → TYPING → (preview变化) → UPDATING → (send) → COMMITTING → IDLE
                   ↑___________|
                每次文字变化都回到这里

异常：焦点丢失/用户手动操作 → 回退 HUD 模式
```

### 核心状态

- `typed_text`：当前已打进目标输入框的文字
- `preview_window`：preview 开始时记录的前台窗口句柄 + 焦点控件句柄

### Diff 算法

语音识别的文字变化通常是"往后追加"或"末尾修正"，公共前缀匹配足够：
- "你好" → "你好世界"：公共前缀"你好"，只需打"世界"（2字新增，0字删除）
- "你好世界" → "你好石阶"：公共前缀"你好"，删2字打2字

### SendInput 性能

| 操作 | 耗时 | 人能否感知 |
|------|------|-----------|
| 100次独立 SendInput 调用 | 约 10-50ms | 完全无感 |
| 1次 SendInput 批量发100个按键 | 约 1-5ms | 完全无感 |
| 对比：一次剪贴板粘贴 Ctrl+V | 约 5-20ms | 无感 |

- 100次退格比一次粘贴还快，人眼感知门槛 100ms
- SendInput 事件进 Windows 输入队列，不会丢，最多排队延迟
- 语音输入一句话通常 10-50 字，极端 100-200 字，都在毫秒级

### 焦点检测

分层策略：

1. **窗口变了** → 一定回退（`win32gui.GetForegroundWindow()`，项目已用）
2. **控件变了** → 一定回退（`win32gui.GetGUIThreadInfo` 的 `hwndFocus`）
3. **光标在同一控件内移动** → 尽量检测（`rcCaret` 坐标），检测到就回退，检测不到就随它去

前两点能挡住绝大多数情况，第三点不是每个应用都靠谱。

### 悬浮窗模式 vs 直接输入模式对比

| | 悬浮窗模式（现在） | 直接输入模式（新） |
|---|---|---|
| preview 阶段 | 文字只在悬浮窗显示 | 文字直接打进输入框 |
| 能不能中途切窗口 | 能 | 不能 |
| 视觉效果 | 悬浮窗预览 | 输入框逐字出现，像输入法 |
| 撤销 | 一次粘贴，Ctrl+Z 一步 | 删-贴，Ctrl+Z 一步 |
| 适合场景 | 多窗口切换、不确定打哪 | 目标明确、想要沉浸感 |
| 复杂度 | 低（已实现） | 中（状态机+diff+焦点检测） |

## 落地实现（2026-09-13）

上屏方式从二选一变成三选一，新值 `direct`（菜单/下拉框显示「模拟键盘（直接输入）」）：

| 取值 | 含义 |
|---|---|
| `paste` | 剪贴板 + Ctrl+V（默认） |
| `type` | 模拟键盘，只在 send 时一次性敲入 |
| `direct` | 模拟键盘，preview 期间就增量打到光标处，send 时只做最后修正 |

接入点：

| 文件 | 改动 |
|---|---|
| `phonemic/gui/direct_input.py` | 新增：会话状态机 + 公共前缀 diff + 焦点指纹 |
| `phonemic/gui/text_input.py` | 新增 `send_backspace()`，抽出 `_send_groups()` |
| `phonemic/gui/keyboard.py` | 三路分发 + `preview_text()`（preview 事件入口）+ `discard_preview()` |
| `phonemic/PhoneMic.py` | preview 分支：直接输入已上屏时不再显示悬浮窗 |
| `phonemic/utils/command_processor.py` | `process_send_text(before_execute=...)`：命中后、执行前的回调钩子 |
| `phonemic/gui/{dashboard,tray,settings_dialog}.py` | 三处菜单各加一项 |
| `phonemic/utils/settings_manager.py` | 白名单加 `direct`（漏改会被静默重置为 paste） |

与原方案 A 的两处偏差：

1. **send 不再「全删 + 重新粘贴」。** 语音识别最后一条 preview 通常就等于最终
   文本，全删重贴既多一次闪烁又要动剪贴板（与「也是模拟键盘」的定位矛盾）。
   现在 send 只是「再做一次 diff」，多数情况下是空操作。代价是 Ctrl+Z 的撤销
   粒度：逐字敲入在部分程序里会被拆成多步撤销，不像一次粘贴那样原子。
2. **焦点丢失后不补发。** 已往旧窗口打过字时，即使焦点换了也不在新窗口补一
   次，否则同一段话会出现两遍。一个字都还没上屏时才允许调用方退回普通上屏。
3. **退格按 Unicode 码点计，emoji 不特殊处理。** 注入是 UTF-16 码元粒度
   （emoji 拆成代理项对、两次 `KEYEVENTF_UNICODE`），但接收方会合成成一个字符，
   一次 Backspace 就删掉它——实测一致，所以一个 emoji 对应一次退格。
   唯一对不上的是 ZWJ 组合（👨‍👩‍👧 这类 5 个码点 = 1 个字形），大多程序按
   字簇处理，可能多删；ASR 基本不会输出，暂不处理（Python 标准库也没有
   grapheme 切分，引入第三方不值得）。

### 命中语音命令时先撤销（2026-09-14 补）

命令往往只是按个回车、发个快捷键，preview 阶段打出的「回车」这类字面文字必须
**先删干净再执行**，否则会和命令效果一起留在目标程序里。流程是：

preview（已上屏部分文字）→ 收 send → 匹配命令 → **命中则撤销 preview 文字**
→ 执行命令；未命中才走 `flash_insert()`。

撤销走 `direct_input.discard()`，两条硬约束：焦点已不在锚点时**绝不发退格**
（那会删掉新窗口里用户自己的内容），撤销失败也不阻塞命令执行，只记日志。

#### 已知限制：撤销类命令（Ctrl+Z / Ctrl+Y）

命令「回退 → ctrl+z」实测表现：说「回退」→ preview 已把「回退」打进文档 →
命中命令 → 先退格删掉 → 再发 Ctrl+Z → **Ctrl+Z 撤的正是刚才那次删除**，
「回退」又原样回到文档里。

根因不在 PhoneMic 这一侧：只要我们在文档里留下过任何编辑痕迹（打字算、退格
也算），目标程序的撤销栈里就有它，Ctrl+Z 必然撤我们的动作而不是用户的。要让
撤销类命令正确工作，只能**一个字都不往文档里写**，即在 preview 阶段预判
「这句话会不会命中命令」、命中则完全不打（方案 A）。但手机端语音的中间结果
随机且快速，预判需要维护命令前缀树，regex 命令还无法预判部分匹配，机制复杂度
与收益不成正比——**不做，改为在用户指南里说明**：撤销类命令建议搭配剪贴板
上屏方式使用（一次粘贴在撤销栈里只算一步）。

## 结论

悬浮窗"不挑输入框、不挑窗口、不怕光标乱跑"，简单可靠。直接输入模式虽然视觉效果好，但焦点检测和边界情况复杂，收益不大。搁置。

> 2026-09-13 补：结论已作废——直接输入作为可选项实现了，默认仍是剪贴板。
> 焦点检测的实际复杂度比预估低（只需比对前台窗口 + 焦点控件句柄），
> 真正难的是「已经打上去的字怎么收拾」，这部分按上面的取舍做了保守处理。
