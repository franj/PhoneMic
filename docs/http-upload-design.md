## 1. 为什么要改 【背景】

### 1.1 现在怎么传 【背景】

手机把文件切成块，一块一块通过 WebSocket 发出去；服务端每落盘一块回一帧 ack，最后一块「收齐」后再回一帧 end ack，手机拿到它才算成功。

### 1.2 慢在哪：片小 × 停等 【背景】

先看现在这套参数（`mobile.html` 的 `LINK_CF` 档案）：

- `chunkMax = 256KB`（CF 档的块上限）
- `MAX_INFLIGHT = 1`（**停等**：收到上一块的 ack 才发下一块）
- 代码注释里的实测：**「一块要 8~10s 才走完」**

代进去算：

```
有效吞吐 ≈ 片大小 ÷ 每片来回时间 ≈ 256KB ÷ 9s ≈ 28KB/s
```

也就是说 100MB 的文件要传大约一小时。瓶颈**不是**「WebSocket 这个协议慢」——WS 传二进制很快——而是：

**片被切得很小，而每一片都必须等一个来回才敢发下一片，于是链路大部分时间在「等」而不是在「传」。**

#### 但 CF 下还压着第二重瓶颈，调参绕不过去 【背景】

上面「片小 × 停等」是**应用层**的自我克制：调大块、放开在途数量就能改善（局域网正是如此）。**Cloudflare 隧道里还压着一层基础设施层面的限制，调参救不了。**

第三方实测（Cloudflare Tunnel 上的 WebSocket）：

- **CF 对上行（client → origin）有字节速率限制，第三方在 WS 上实测约 0~1 Mbit/s**；而 origin → client（下行）不限速，能跑满。⚠️ **本机复测显示 HTTP PUT 也贴着同一个上限（≈1 Mbit/s）** ⇒ 这条整形**与上层协议无关**，换协议只是能把它用满（见下表下面的推断）；
- **256 KiB 的 WS 帧会被 CF 截断/重置**，32 KiB 才稳定；
- 限速不只是「慢」：持续上传约 5MB / 40s 后 **CF 会主动断开连接**。

拿本机实测对照（**09-20 复测后的数字**）：

| 来源 | 数字 | 换算 |
|---|---|---|
| CF 下 WS 实测 | ≈ 20 ~ 30 KB/s | 0.16 ~ 0.24 Mbit/s |
| 代码里那句「一块要 8~10s」（`LINK_CF.chunkAck` 注释） | 256KB ÷ 9s ≈ 28 KB/s | 0.23 Mbit/s |
| 第三方实测的 WS 上行限速区间 | 0 ~ 1 Mbit/s | 0 ~ 128 KB/s |
| **同一条隧道上 HTTP PUT 实测（稳定值）** | **≈ 120 KB/s** | **≈ 1 Mbit/s** |
| 同一条隧道上 HTTP PUT（**一次性偶发**） | 6 MB/s | 48 Mbit/s |

**一个把两组数字串起来的推断**：CF 对**上行**（client → origin）的整形上限似乎就在 **≈1 Mbit/s** 上下，**与上层是 WS 还是 HTTP PUT 无关**。WS 只跑到 0.2Mbit/s —— 因为它被「片小 × 停等」自己卡住了、**并没把限额用满**；换成分片 PUT 之后跑出 ≈1Mbit/s，**正好贴着这个上限**。

⇒ 所以「4~5 倍」这个数的准确含义是「**从用不满限额，到用满限额**」，而不是「HTTP PUT 这个协议比 WebSocket 快」。这也顺带解释了两件事：① 为什么调 WS 参数救不回来（限额就摆在那，调到最优也只有 1Mbit/s）；② 为什么不该指望 PUT 能再往上翻（它已经在顶了）。

⚠️ **「快」不是常态，「被限制」才是。** 上表最后那行 6MB/s 是 CF 限速整形尚未生效的窗口，**不可复现、不可依赖**；稳定值就是 ≈120KB/s，单片与分片都一样。

⇒ 三条结论（修正后）：

1. **瓶颈在 CF 对上行带宽的整形，不在本项目代码、也不在协议。** CF 免费隧道下上行就是百 KB/s 量级，**这是基础设施的天花板**；HTTP PUT 拿到的是这个天花板下最好的结果（**约 4~5 倍于 WS**），而不是绕过天花板。
2. **4~5 倍仍然值得做**，但理由要换一个：WS 那 20~30KB/s 还叠着第二个问题 —— **256KB 的块正好踩在 CF 的截断/重置区间**，且持续上传约 5MB/40s 会被主动断连 ⇒ 它是个**不稳定**的 30KB/s。100MB 按 120KB/s 约 14 分钟，按 30KB/s 约一小时。
3. **局域网下才是纯粹的提速。** 同一份代码在 LAN 上实测「**40MB 瞬间到达**」——那不是倍数的问题，是量级差。

### 1.3 那为什么片只能这么小 【背景】

因为**WS 帧发失败了，发送端不知道丢在哪**。发出去一帧，没有响应告诉它「对方收到了多少、写进去没有」，于是只剩两个保守选择：片切小（丢一片损失小）、一次只敢在途一块（否则失败了不知道该重发哪一段）。`bufferedAmount` 帮不上忙——它只覆盖「浏览器自己还没发出去的部分」，再往后的手机内核、无线、CF 回源、PC 内核、写盘全是盲区。

### 1.4 你感觉到的三件事，其实是同一个根因 【背景】

| 你感觉到的 | 直接原因 | 根子上的原因 |
|---|---|---|
| 慢 | 片小 × 停等 | 失败无法定位 ⇒ 不敢用大片、不敢放开在途数量 |
| 进度不准 | 只能「本地估算 + 最多一块前瞻」（`_progressTick`），真值在服务端手里但传不回来 | WS 没有响应通道 |
| 不能实时取消 | 只能发一帧 cancel 再等回执（三级等待 + `hello` 探活兜底） | WS 没有「取消」这个动作 |

三条都是「**WS 没有请求/响应语义**」这一个缺陷的不同侧面。

### 1.5 换成 HTTP PUT 之后 【背景】

HTTP 一次请求就是一次结果，于是：

| 收益 | 为什么 | 实测 |
|---|---|---|
| **快** | 响应带来「精确失败位置」（409 里带 `received`）⇒ 敢用 15MB 的大片 ⇒ 每片来回时间里的 RTT 部分被摊销掉 **60 倍**（256KB → 15MB）。WS 那套「停等」的自限没用满 CF 给的额度，换 PUT 之后贴到了上行整形的天花板上 | CF：**≈4~5 倍**（30KB/s → 120KB/s，且从「不稳定」变成「稳定」）；LAN：**40MB 瞬间到达** |
| **进度准** | 进度是服务端确认**收到**的字节数，不再需要客户端估算 | ⚠️ **片粒度准，片内是死区** —— 09-23 真机后补 `upload_progress`（§5.13） |
| ~~取消实时~~ → **取消可用** | ⚠️ **不是 `xhr.abort()` 自动生效** —— 实测点取消之后服务端照收不误（§5.6.1）。真正起作用的是取消时**额外发一个 WS 帧**让服务端作废会话、丢掉已读字节 | 见 §5.6 |

> ⚠️ 第三条是 v3 修订的重点：v2 把「服务端收到 `ClientDisconnect` 就会停」当成免费的收益，**实测证明它不成立**。取消仍然要一条显式信号，只是这条信号走 WS（`upload_cancel`），而不是 v2 计划的 HTTP `DELETE`。

> ⚠️ 第二条同样被真机修正（09-23）：v3 以为「HTTP 响应带回 `received`」就等于「进度准」，但 CF 是**先收后转**的代理 —— 手机把 15MB 交给 CF 只用几秒（`xhr.upload.onprogress` 立刻冲到 100%），CF 再以 ≈100KB/s 回源，**响应要两三分钟后才回来**。于是进度条的真实形态是「几秒满格、然后横住两分钟」。⇒ 片粒度上的 `received` 不够，还需要一条 PC 主动推的**片内**进度（`upload_progress`，§5.13）。

### 1.6 代价（必须认账） 【背景】

| 代价 | 说明 | 对应章节 |
|---|---|---|
| Cloudflare 单请求 100MB 硬限 | 免费/Pro 计划，超过在**边缘**就被 413 拒绝，PC 根本收不到字节 ⇒ 必须分片。15MB 一片留了 6 倍余量 | §2.2 |
| body 要自己加密 | 头里的签名只认证请求，不保护文件内容（加密永远开启，没有明文分支） | §2.1 / §5.4 |
| 需要一张「上传会话表」 | HTTP 请求是独立的新连接，服务端看不出它属于哪条 WS ⇒ 要靠 `sid` 关联 | §4.2 |
| 加密层要动一刀 | 现有的防重放 seq 和加解密是焊在一起的，需要拆一层 | §5.8 |

## 2. 三个必须先解决的问题 【规范】

### 2.1 头里认证 ≠ body 加密 【规范】

「把服务端给的随机数加密后放进 HTTP 头」完成的是**请求认证**（证明你持有那把钥匙），**body 本身还是原始字节**。

而现在的加密设计（见 `crypto-design.md` §2）的立足点正是：Cloudflare 模式下 TLS 在边缘就终结了，隧道段是裸的——所以连鼠标事件的 `type` 都不许明文。如果上传走明文 body，就变成「文字是端到端加密的、文件却不是」，这个裂缝没法用「反正有 HTTPS」搪塞过去：**「有 HTTPS」正是我们要防的那一层**。

处理见 §5.4：**body 永远自己加密**——项目已无明文模式（见 §5.3 的代码事实）。

### 2.2 Cloudflare 免费/Pro 计划单请求体上限 100MB 【规范】

超过这个大小，请求在 Cloudflare 边缘就被拒绝（413 Request Entity Too Large），**PC 端根本收不到任何字节**（Free/Pro = 100MB，Business = 200MB，Enterprise = 500MB 起）。

对比现在的 WS 分块：每块是一帧小消息，**没有这个限制**，所以现在能传 1GB。

⇒ 也就是说，「一个 PUT 传整个文件」相对现在是**功能倒退**。**必须分片**（定为每片 15MB）。⚠️ 分片本来还白送一个好处——「传一半断了只需重传那一片」；**09-23 之后连它也不做了**（§5.6.4：失败即放弃整个上传），所以分片保留的理由只剩「CF 单请求 100MB 硬限」本身。

### 2.3 「一次性」应该定义在文件范围，而不是请求或片 【规范】

你原来的想法是「随机路径 + 随机数认证，一次性的，防重传」。这里需要先把「一次性」的作用域定清楚，因为它和 HTTP 的重试语义直接冲突：

| 作用域 | 后果 |
|---|---|
| 整个 HTTP 请求 | 重试必被拒；响应一丢就得重走一整轮 WS 协商，而这次协商本身也可能再失败。且失败不可区分（分不清「服务端没收到」和「收到了但响应丢了」） |
| 单个片 | 等于每片发一张票据 ⇒ 要么每片多一次 WS 往返，要么服务端预生成一堆票据 |
| **整个文件（采用）** | 一次协商、一个 `sid`、**N 个片共用**；重放与错位都在片内消化 |

「整个文件一次性」的防重放含义是两句话：

1. **一个 `sid` 只能落成一个文件**：不能用它写第二条路径、传第二个文件、改 `size`、改落盘名——这些在 `upload_begin` 时就全部固定死了；
2. **同一 `sid` 内的重复片不会造成第二次写入**，由偏移规则（§5.5）与加密层自带的片序号（§5.4 / §5.8）两处拦住。

这样「重放」被干净地挡住（忽略），而不是把整条上传一起拒掉。

## 3. 一次上传的完整流程 【规范】

以「手机上传一个 40MB 的文件到电脑」为例。以下每一步都标注：谁发给谁、带什么、服务端在做什么。

```
手机（页面）                                            服务端（PC）
   │
   │ ① WS   upload_begin
   │        {ref:"file", name:"movie.mp4", size:41943040}
   │──────────────────────────────────────────────────────────────►│
   │                                    校验类型与大小上限
   │                                    分配落盘名（重名自动改号）
   │                                    建「上传会话」：sid + 有效期
   │
   │ ② WS   upload_ready
   │        {id:1, sid:"…", chunk:15728640, saved:"movie.mp4", expires:600}
   │◄──────────────────────────────────────────────────────────────│
   │
   │ ③ HTTP PUT  /api/upload/<sid>                    ← 第 0 片
   │      X-Pm-Offset: 0
   │      X-Pm-Len:    15728640
   │      X-Pm-Mac:    <用上传密钥算的签名>
   │      body:        nonce(24B) ‖ 密文体 ‖ tag(16B)，共 len+48（§5.4）
   │──────────────────────────────────────────────────────────────►│
   │                                    验签 → 校验 offset → 解密 → 写 .part
   │      200  {"received": 15728640}
   │◄──────────────────────────────────────────────────────────────│
   │
   │ ④ PUT 第 1 片（offset=15728640）… 200 {"received": 31457280}
   │
   │ ⑤ HTTP PUT  最后一片（offset=31457280，len=10485760）
   │──────────────────────────────────────────────────────────────►│
   │                                    收齐 ⇒ 收尾：.part 改名落盘
   │                                    （photo 则写系统剪贴板、不落盘）
   │      200  {"done": true, "saved": "movie.mp4"}
   │◄──────────────────────────────────────────────────────────────│
```

**几个要点：**

1. **① ② 是本流程唯一的 WS 消息**（① 被拒时换成 `upload_error`，§5.1），一次传输只发生一次（一个来回）。之后所有数据都走 HTTP，WS 不再参与——**只剩「取消 / 断连」这个控制面还挂在它上面**（§5.6）。
2. **`sid` 是服务端生成的会话号**，客户端把它拼进 URL。服务端靠它把「这条 HTTP 请求」和「刚才那次协商」对上——这是 HTTP 被允许上传的全部理由（见 §4.1）。
3. **签名（`X-Pm-Mac`）的作用是「读 body 之前先拦一道」**，用的是**本次上传专用的一把钥匙**（从哪来见 §5.9），**不需要任何新的握手**（见 §5.3）。内容本身的保护由 body 的加密负责（§5.4）。
4. **片的顺序由 offset 表达，服务端严格按 offset 推进**；客户端**逐片串行发**（收到响应才发下一片——③④⑤ 各一个来回），这是密文里片序号能接上的前提（§5.8）。响应里的 `received` 就是「已收下的字节数」，客户端用它**确认本片**并画进度条（**不再用它续传**，§5.6.4）；片**内**的进度由服务端主动推的 `upload_progress` 帧提供（§5.13）。
5. **没有「结束」请求**：最后一片落地时服务端自己收尾，响应里的 `done: true` 就是终局。这比现在的 end ack 更硬——HTTP 响应是在 `.part` 改名落盘**完成之后**才发出的。
6. **取消是唯一需要「额外来一条」的动作**，而且它**不在上面这张图里**——因为它是带外的：⑥ 用户在任意时刻点取消 → 客户端 `xhr.abort()` **并追加一帧 WS `upload_cancel`** → 服务端作废会话、一个字节都不落盘。为什么必须这样，见 §5.6.1。

## 4. 关键概念 【规范】

### 4.1 为什么不能「复用 WS 那条连接」 【理由】

这是最容易卡住的一点，单独说清楚。

**WebSocket 连接和 HTTP PUT 是两条完全独立的 TCP 连接。**服务端收到一个 PUT 请求时，手上只有：来源 IP、请求头、URL、body。它**没有任何办法**知道这个请求和刚才那条 WS 有关——不是实现没做好，是 HTTP 协议里根本没有这个字段。

打个比方：你刚打完电话（WS），现在要寄一个包裹（PUT）。快递员不知道这包裹和那通电话有什么关系，所以**包裹上必须贴一张双方认得的封条**。

所以整件事被拆成两个独立问题：

| 问题 | 答案 | 在哪一节 |
|---|---|---|
| 封条用什么做？ | 用**本次上传专用**的一把钥匙算签名（从哪来见 §5.9） | §5.3 |
| 服务端怎么知道这包裹属于哪次会话？ | URL 里的 `sid` | §5.2 |

**都不需要重新握手**：钥匙在 WS 握手时就已经换好了，两端各有一份。

### 4.2 上传会话（`sid`） 【规范】

`upload_begin` 时服务端建一条记录，内容大致是：

| 字段 | 说明 |
|---|---|
| `sid` | 会话号，24 字节随机（base64url），既当标识也用当路径 |
| `kind` | `file`（落盘）还是 `photo`（写剪贴板） |
| `name` / `size` | 客户端声明的文件名与明文总字节数 |
| `saved` | 服务端分配好的最终文件名（重名已改号） |
| `received` | 已收下的明文字节数。**唯一权威**：本片是否成功看它；进度条也看它 |
| `key` | 上传密钥 `k_mac` / `k_body`：本次上传新协商的一次性密钥（§5.9 方案二）。**不会是 `None`** —— 上传只在加密模式放行（§5.4） |
| `expires_at` | 过期时刻（**每次收到合法分片就向后顺延**） |

生命周期：

- **建立在 ①，正常结束在 ⑤**；
- **生命周期 ⊆ WS 连接的生命周期**（09-23 修订，取代 v3 的「不绑定连接」）：WS 一断，该连接名下的**所有**上传会话立即作废——删 `.part`、摘除密钥。理由见 §5.6.4；
- 会话的凭据仍然是 `sid + k_mac/k_body`（不是「哪条连接」），但这话只在**会话活着**的期间有意义：「跨重连继续传」**不做**（§9-4）；
- **一次会话只服务一个文件**（§2.3）。想在同一个 `sid` 上换文件名、换大小、传第二个文件，一律拒绝；
- 过期或被清理时 `sid` 失效 → 后续 PUT 走 §5.10 的「拿不出凭证」分支（不读 body、直接关连接）→ 客户端放弃这次上传并提示用户；下次上传重新走 ① ②；
- 收尾后**不立刻删除**，保留到过期：这样「最后一片的响应丢了、客户端重传」也能拿到幂等的 `done`（命中 §5.5 第二行），但**不会产生第二个文件**（落盘名已固定、偏移不会推进）。⚠️ 客户端**不再重传**（§5.5 / §5.6.4）——这一支留着是为了「重放不产生副作用」，不是给重试用的。

> `sid` 放在 URL 路径里，因此会出现在 uvicorn 的访问日志中。它**不是凭据**（真正的门禁是签名与加密），所以可接受；但它**必须保持 192 位真随机**——它是路径里唯一的选择器（§5.2 起上传请求不再带页面前缀），也决定了「猜得到就能试」的难度。

## 5. 设计细节 【规范】

### 5.1 新增的 WS 消息 【规范】

**上行**

```json
{"type":"upload_begin", "id":1, "ref":"file", "name":"a.pdf", "size":41943040}
```

| 字段 | 说明 |
|---|---|
| `id` | 传输号，**客户端分配**（沿用 `file` / `photo` 的语义：连接内单调递增），服务端原样回显——`upload_ready` / `upload_error` 都靠它和 UI 对号 |
| `ref` | `"file"`（落盘）或 `"photo"`（写剪贴板） |
| `name` | 原文件名，`photo` 可省略（剪贴板没有文件名概念） |
| `size` | **明文**总字节数（不是密文，也不是分片后的） |

**下行**

```json
{"type":"upload_ready", "id":1, "sid":"…", "chunk":15728640, "saved":"a(1).pdf", "expires":600,
 "k_mac":<bin32>, "k_body":<bin32>}
```

| 字段 | 说明 |
|---|---|
| `id` | 回显 `upload_begin` 的 `id` |
| `sid` | 上传会话号 |
| `chunk` | **服务端建议的片大小**（明文字节，当前 15MB）。放服务端下发，是为了将来调参不用改手机页面 |
| `saved` | 最终文件名（已处理重名），客户端可直接显示「将保存为 a(1).pdf」 |
| `expires` | 会话有效期（秒），描述性字段，不作为判据 |
| `k_mac` / `k_body` | **本次上传专用的两把 32 字节密钥**（§5.9 方案二）：`k_mac` 签 `X-Pm-Mac`，`k_body` 用来建**上传专用的 Provider 实例**（§5.8，与跑 WS 的那个分开）。整帧已被 WS 会话密钥加密，所以它们以明文放在帧里。⚠️ 三条卫生要求见 §5.9；**这一帧禁止进 trace 日志** |

**上行（取消）**

```json
{"type":"upload_cancel", "sid":"…"}
```

| 字段 | 说明 |
|---|---|
| `sid` | 要作废的上传会话号 |

**没有对应的下行回帧。** 取消是**单向、幂等**的通知：失败也不致命（TTL 兜底，§5.6），而客户端此刻本来就已本地 `abort()`、UI 已切回「未开始」——**不需要服务端确认**。所以 `cancel` 帧不再有 ack，也不用 `hello` 探活兜底（§8）。

> **为什么不是 HTTP `DELETE`** —— v3 的核心修订，见 §5.6.1。一句话：实测 `xhr.abort()` 停不下服务端，所以「取消」必须走一条**已经认证过、且不排在那条正在传 body 的连接后面**的通道，那就是 WS。

**被拒**

```json
{"type":"upload_error", "id":1, "code":"too_large", "msg":"photo too large"}
```

| 字段 | 说明 |
|---|---|
| `id` | 回显 `upload_begin` 的 `id` |
| `code` | 机器可读的分类，见下表 |
| `msg` | **只给日志 / 调试**的英文短语。⚠️ 界面文案**不要**直接显示它——由客户端按 `code` 走自己的语言包（否则文案语言跟着电脑走，与手机界面不一致） |

| `code` | 含义 |
|---|---|
| `too_large` | 超过该类型的大小上限（§5.7） |
| `bad_ref` | `ref` 不认识 |
| `bad_args` | 参数缺失 / 不合法（含 `size` 与声明不符等） |

在 ① 阶段就拒（此时 `size` 已知，还没传一个字节）。

> **为什么单开一个 `upload_error` 而不复用 `error`**（09-23）：`error` 是**连接级**的通用通道（`auth` / `malformed` / …），上传的失败面是**流程内**的（要跟 `id` 对号、要跟那条进度气泡联动）。混在一个 type 里，客户端分派表就得写成「先看 `type` 再看 `code` 才知道这是不是上传的事」——这正是协议层该消掉的模糊。⇒ 上传相关的拒绝一律走 `upload_error`，`error` 保持它原有的通用语义。

> 为什么协商这一步不能省？因为它顺带做完了三件事：**校验大小**（避免白传）、**分配最终文件名**（重名编号只算一次）、**建立密钥绑定**（HTTP 请求才能验签与解密）。代价在局域网是几毫秒，在 Cloudflare 上是几十到几百毫秒——相对传输本身可忽略。

**进度（下行，周期性）**

```json
{"type":"upload_progress", "sid":"…", "received":4194304}
```

| 字段 | 说明 |
|---|---|
| `sid` | 所属上传会话。**跟它对号，不是跟 `id`** —— 进度是会话级的，与哪一次 `upload_begin` 无关 |
| `received` | 服务端**已收下**的明文字节数（含当前这一片中已经到达的部分） |

⚠️ **它不参与任何状态判定**：可丢、可晚到，收尾只看 HTTP 响应。为什么需要它、多久推一次，见 §5.13。

### 5.2 HTTP 端点 【规范】

```
PUT    /api/upload/<sid>     上传一片
```

**只有这一个端点。** v2 曾计划再加一个 `DELETE /api/upload/<sid>` 承载取消，**v3 已整体删掉**，取消改走 WS 帧 `upload_cancel`（§5.1）。理由见 §5.6.1——那是本次修订里最实质的一处改动。

签名：

```
mac = BLAKE2b(k_mac, "PUT" + "\n" + sid + "\n" + offset + "\n" + len)
```

> 删掉 `DELETE` 顺带消掉三样东西：一个破坏性端点、一套「验签先于副作用」的顺序约束、以及「`DELETE` 也要排空 body」的额外分支（§6.1）。

**没有页面前缀**（09-23 决定，取代 v3 的「客户端写相对路径、由浏览器自动带上页面前缀」）：URL 固定是 `/api/upload/<sid>`，客户端写**根绝对路径**。

理由是「页面前缀只在页面加载那一刻有意义」：

| | 页面前缀是什么 | 为什么上传不该带它 |
|---|---|---|
| 它提供什么 | 防扫描：把「这个端口在跑 PhoneMic」的可见度降下来（§5.11.5） | 上传**不需要**靠路径当凭据——它自带 `k_mac` 独立认证（§5.3），正符合 §5.11.5 那条「有副作用的端点必须独立认证」 |
| 它保护什么 | 入口页 + JS（**一次性**加载的东西） | 上传 URL 会出现在**每一片**的请求行与访问日志里 ⇒ 等于把入口前缀**持续**广播出去，而它本来只需要在加载页面那一刻出现 |
| 会话标识靠谁 | — | `sid` 已是 24 字节真随机（§4.2），做选择器足够 |

⇒ 代价是服务端要在**两种认证模式下都**给 `/api/upload/` 开一条前缀放行（§6.2）——这两行代码比「每片都带一个不该带的秘密」划算。

> ⚠️ 客户端别写相对路径（`api/upload/<sid>`）：页面在 `/<secret>/` 下时它会变成 `/<secret>/api/upload/<sid>`，落进 `secret_path` 分支里的**另一条**路径。一律写 `/api/upload/<sid>`。

请求头：

| 头 | 说明 |
|---|---|
| `X-Pm-Offset` | 本片在**明文**文件中的起始偏移 |
| `X-Pm-Len` | 本片**明文**长度 |
| `X-Pm-Mac` | 签名，见 §5.3（**必有**——项目没有明文模式） |
| `Content-Type` | `application/octet-stream` |
| `Content-Length` | 本片**密文**长度 = `X-Pm-Len` + 48（恒等式，与算法无关，§5.4） |

服务端应先做一个零成本的一致性检查：`Content-Length` 与 `X-Pm-Len`（+ 固定开销）对不上就直接 400，不必读 body。

响应：

| 状态 | 含义 | body |
|---|---|---|
| 200 | 本片已落盘；**或**是重复片（不写入） | `{"received": N}`，若全部收齐再加 `{"done": true, "saved": "…"}` |
| 400 | 头之间自相矛盾（长度不符等） | — |
| 401 | 签名不对 / 会话不存在 / 已过期 | — |
| 409 | 偏移不是「当前该写的那一段」（跳片 / 部分重叠） | `{"received": N}` |
| 413 | 超过声明大小或上限 | — |
| 500 | 服务端内部错误 | — |

⚠️ **只有 401 那一行不碰会话**（它出现时验签还没过）；**其余非 200 一律作废这次上传**（删 `.part`、摘除密钥），判定与分类见 §5.5。

> **401 绝不能顺手作废会话**：LAN 下 `sid` 在 URL 里是明文可见的（§5.11.3），一个只知道 `sid` 的人随便发个签名错的 PUT，如果它就能把会话作废，那**一个未认证的包就能毁掉别人正在传的文件**。⇒ 作废只发生在**验签通过之后**的分支——这也是 §5.10 那条「拿不出凭证 ⇒ 不读 body、直接关连接」的另一个用处。

**`received` 是客户端进度的唯一依据**：它等于「服务端已收下的字节数」，比现在「本地估算 + 一块前瞻」准得多。⚠️ 但只有它还不够 —— 它只在**整片收完**时才回来一次，CF 上一片要两三分钟（§5.13），所以片**内**还要一条 PC 主动推的进度帧。

#### 可选：元信息要不要用 msgpack 打包、加不加字段 【理由】

客户端侧 msgpack 是**现成的**（`msgpack.min.js`，WS 帧本来就用它编解码），拿它打包元信息不增加依赖。但**放哪受一条硬约束限制**：

> **服务端必须在读 body 之前就能拒掉它不感兴趣的请求。**否则一个未认证的客户端就能逼你读完 15MB 才回 401（§6.1）。

所以字段要先分两类：

| 类别 | 字段 | 放哪 |
|---|---|---|
| **必须能提前看到** | `sid`（在 URL 里）、`offset`、`len` | HTTP 头（现在这样就够） |
| 可以后看到 | `v`（上传协议版本）、文件名、`kind`、总大小 | 头 / body / 甚至不用传（已在 ① 的 WS 消息里定过了） |

两种打包方式：

- **(a) 打包成一个头**：`X-Pm-Meta: base64url(msgpack({...}))`。加字段不用新增头名；但 base64 之后人不可读，调试和 `curl` 手测（§10 阶段 2）会变难。
- **(b) 放进 body 明文前缀**：`body = 前缀长度(4B) ‖ msgpack(meta) ‖ 密文`。不占头、无 base64、结构随便加；代价是 `Content-Length` 与「明文片长」之间多一层换算。

**建议 v1 就用上面那三个显式头**，理由是**人能直接看懂**，而阶段 2 的验证完全靠 `curl` 手工发片。将来字段真多起来了再上 (a)。

**要加什么字段才值得？** 老实说大部分已经在 ① 的 WS 消息里定死了（`name` / `size` / `kind` / 落盘名），HTTP 侧再传一遍只会多出「两处不一致该信谁」的问题。**真正值得新增的其实只有 `v`（上传协议版本）**：它让将来改协议时服务端能明确拒绝旧客户端，而不是靠猜。

### 5.3 请求认证：用上传密钥算签名 【规范】

方式是在头里放一个**签名（MAC）**，用的是一把**只属于这次上传的对称密钥**（从哪来说 §5.9，这里先只讲怎么用）：

```
k_mac = 上传密钥之一（32 字节，见 §5.9）
mac   = BLAKE2b(k_mac, "PUT" + "\n" + sid + "\n" + offset + "\n" + len)
```

服务端用同一把 `k_mac` 重算一遍，比对一致就放行。**这就是 HMAC 那类东西**：它不隐藏内容（内容由 §5.4 的加密负责），只负责证明「这串数据是我发的、没被动过」。

三个细节：

1. **签的内容必须包含 `sid`、`offset`、`len`，不能只签一个随机数。**否则攻击者可以拿一份合法签名配上改过的偏移，去覆盖文件的别的位置。方法名 `"PUT"` 也签进去，防止签名被挪用到别的请求上。
2. **用 keyed BLAKE2b 当 MAC，不用 `crypto_auth`。** 两端各一行，而且是同一个构造：

   ```
   Python: hashlib.blake2b(msg, key=k_mac, digest_size=32).digest()
   JS:     sodium.crypto_generichash(32, msg, k_mac)
   ```

   ⚠️ **别写 libsodium 的 `crypto_auth`**：它只有 JS 侧有（`sodium.crypto_auth`），**PyNaCl 1.6 的 `nacl.bindings` 里没有它**（`crypto_onetimeauth` 也没有）⇒ 真按 `crypto_auth` 写，服务端一调用就 `AttributeError`。keyed BLAKE2b 是两端都有的同一条 libsodium 构造，而且**本项目已经在用它做 KDF**（`key_exchange.py` 的 `hashlib.blake2b` / `crypto_providers.js` 的 `sodium.crypto_generichash`），换上去零新增依赖、也不会出现两端算法不一致。
3. **比较要恒定时间**（`hmac.compare_digest`），避免按字节比较泄漏信息。

**它的准确定位是「读 body 之前的门禁」**：有了它，一个明显不属于我们的请求可以在传 0 字节的情况下被 401 掉；**没有它也不影响内容的机密性与完整性**（那是 body 加密的职责）。如果将来要砍东西，这一层比 body 加密更适合砍。

#### 取消的认证问题：随 `DELETE` 的删除一并消失 【理由】

v2 这里曾有一整节讨论「**`DELETE` 报文来了需要认证吗？不认证的话，局域网里有人知道 `sid` 就能故意删掉？**」——结论是「要，而且用同一把 `k_mac`」，还配了一张「伪造 `PUT` vs 伪造 `DELETE`」的不对称后果表。

**v3 把这一节整体作废，因为它的前提被推翻了**：前提是「取消是一个没有 WS 认证的 HTTP 请求」，而实测证明 `xhr.abort()` 根本停不下服务端（§5.6.1），所以取消必须走**已经认证过的 WS 通道**。`DELETE` 不做了（§5.2），就没有一个「只剩 `sid` 一层门禁」的破坏性端点要讨论。

> 不过那张表揭示的道理仍然成立，而且更值得记住：**`PUT` 与「作废/删除」的后果是不对称的**——伪造 `PUT` 最坏是搞坏一个正在传的文件（还要过 §5.5 偏移幂等与 §5.4 的片序号两道），而伪造「作废」是**不可恢复地毁掉别人正在传的东西**，纯 DoS。所以取消这个动作**不能降级成「`sid` 即凭证」** —— 改走 WS 帧恰好天然满足这一点：WS 在握手时已经认证过（§5.11.5 那条「有副作用的端点必须独立认证」的规则，它免费合规）。

#### 一条代码事实：上传路径上永远有密钥 【理由】

**明文模式已经整体移除**（`docs/e2ee-always-on-design.md`）：`SecureChannel.algorithm` 恒为 `"auto"`、`needs_auth` / `is_encrypted` 恒为 `True`，可选的只剩 `auth_method`（`tofu` / `url_fragment`），**没有任何一条路径能跑出不加密的连接**。`mode.py` 留下的 `effective_auth_method()` 管的也只是认证方式，不再有「把 `none` 抬成 `auto`」这类补丁——因为 `none` 本身没了。

⇒ 结论是：**上传路径上永远有 `k_mac` / `k_body`**（`PUT` 用），不存在「没有密钥」的情况，也就不需要任何「非加密模式禁止上传」的门禁（§9-1 已作废）。

#### 两把钥匙，别用一把兼两职 【规范】

这次上传用**两把 32 字节密钥**，各管一段：

```
k_mac   ──► keyed BLAKE2b，签 "PUT\nsid\noffset\nlen"
k_body  ──► body 分片的 AEAD（§5.4）
```

同一个 CSPRNG 调用生成 64 字节切两半即可，成本为零；不切的话，同一把 key 就同时兼作 HMAC 和 AEAD 两种原语的密钥，没必要。

`k_mac` / `k_body` 从哪来 —— 见 §5.9。两种方案都可行，**推荐每次上传新协商一把一次性钥匙**。

⚠️ **「换钥匙」与「加密走哪条路」是两件独立的事**（§5.9 开头那张表）。方案二选了「每次上传现生成一把钥匙」；「上传片怎么加密」由 §5.8 回答 —— 结论是**什么都不用改**：provider 内部自带的片序号恰好就是上传需要的那个判据，而重放 / 错位在它之前就被 offset 判定截住了。**但这两个决定不能互相替代**：新钥匙负责「会话隔离」（§5.8 前提 2），offset 判定负责「重复与错位」（§5.5）。

#### 不做跨重连 【规范】

上传会话的生命周期**完全落在一条 WS 连接之内**（§4.2，09-23 修订）：WS 一断，该连接名下的会话全部作废。⇒ 不存在「重连之后接着传」，也不用为它保留钥匙、进度或 `.part`；页面刷新同理（客户端连 `sid` 都丢了）。

> 这一条取代了 v3 的「不绑定 WS 是否活着」（当时的理由是「iOS 切后台会让心跳回不去，绑定连接会让上传白废」）。修订理由见 §5.6.4：**留在表里的半成品会话比「上传失败」更难解释**，而且它一次带来三样东西——没被删的 `.part`、还在内存里的钥匙、以及「服务端还在等、客户端已经不打算传了」的错位状态。宁可让它干脆地失败。

#### 能拿到 `sid` 的会话一定有钥匙 【规范】

钥匙由 ① 阶段的协商产生（怎么产生见 §5.9），而明文模式不存在（见上）。⇒ 服务端不需要「有钥匙 / 没钥匙」两条解密路径，少一条分支、少一组测试，也少一个「明文分支忘了走加密」的漏改风险。

### 5.4 body 加密：每片独立加密 【规范】

片与片**互相独立**（指每片自带完整加密信息、不需要别片的上下文；但顺序仍必须连续，§5.8），项目没有明文模式（§5.3）。**加密细节由 Provider 自己完成，上传代码看不见、也不传递任何密钥或上下文**（§5.8）。

**一个 PUT 请求的 body 有且只有这一段密文片**——没有长度前缀、没有 meta、没有分块（元信息全在头里，§5.2）：

```
body = Provider.encrypt( 片序号(8B 大端) ‖ 明文片 )      ← 原始返回值原样发出，不再包一层
     = nonce(24B) ‖ AEAD密文体(8 + X-Pm-Len) ‖ tag(16B)
```

| 段 | 字节数 | 谁产生 | 说明 |
|---|---|---|---|
| `nonce` | 24 | 库，每片随机 | 前置在头部，与现有密文布局一致（`crypto-design.md` §6）。**密文能否解开只取决于「密钥 + 它」，与片序号无关** |
| AEAD 密文体 | 8 + `X-Pm-Len` | AEAD（明文 = 片序号 ‖ 明文片） | 比 `X-Pm-Len` 多 8 字节，是因为片序号焊在明文头部 |
| `tag` | 16 | AEAD（Poly1305） | **在最后** ⇒ 必须收齐整片，才能判断前面那段有没有被动过 |

⇒ **`Content-Length` 恒等于 `X-Pm-Len` + 48**，两种算法的开销完全一致 ⇒ 长度可精确预计算，**不需要 chunked 编码**（CF 对 chunked 请求体更保守）。§5.2 那个「零成本一致性检查」用的就是这个等式。

- **片序号（8 字节大端）**：由 Provider 内部自增，**两种算法写法完全一致**（都拼在明文头部，见 §5.8）。⚠️ **它来自一个只服务本次上传的 Provider 实例**，从 0 起随片递增 ⇒ 实际上就是**片索引**；**不能**与跑 WS 的那个实例共用（原因见 §5.8「为什么必须是另一个实例」）。调用方仍然不需要传任何东西，也不需要知道当前算法是哪个。
- **服务端收齐整片后解密校验**，通过才把明文写进 `.part`，⚠️ **且必须先丢掉前 8 字节**（那是片序号，不是文件内容）。「整片」两个字不能省：**认证标签在密文尾部**（上面那张表里它是最后一段；`tag` 由库追加，**别手动再加一次**），没有 tag 就无法判断前面这段有没有被改；而两端的库都只提供**一次性**接口（已核实：PyNaCl 的 `nacl.bindings.crypto_aead` 只有 `encrypt` / `decrypt`，没有 `init/update/final`；`sodium.js` 同样）⇒ **要么整片收齐，要么不判，中间没有第三种状态**。两个后果：① 内存占用 = 片大小（§6.3）；② 「读了前几字节就判断合法性」做不到（§5.10）。
- ⚠️ **解密必须发生在「offset 判定」之后**（§5.5 三行判定 → §5.8 前提 1）：只有 `offset == received` 的片才允许进入解密；重复片 / 错位片在判定阶段就已经处理掉了。

**没有明文分支**（决定）：body **永远是密文**。明文模式已整体移除（§5.3 的代码事实），所以服务端只有一条解密路径。

> ⚠️ **为什么不用 AAD（09-23 修订）**：曾经的设计是给 XChaCha20 传 `aad = sid ‖ offset ‖ len`，而 XSalsa20 没有 aad 只能走前缀，于是**两种算法两条路径**，还要给 Provider 加新接口。**现已取消** —— 两种算法统一走「8 字节前缀」，理由三条：
>
> 1. **AAD 与「明文前缀」的认证强度完全一样**：AAD 参与 tag 计算，明文也在密文里、同样被 tag 覆盖，两者都被认证。唯一差别是**接收方什么时候读得到它**（AAD 解密前可读、前缀要解密后）。而上传的 `offset` / `len` 是从 **HTTP 头**读的（要做 §5.5 那三行判定），**本来就不在密文里、也不需要进去**。
> 2. **AAD 原本想绑的三样东西，各由别的机制在扛**（下表），删掉不留缺口。
> 3. **删掉之后 `crypto/` 的接口一个字不用改**，调用方零感知 —— 「一个用 aad、一个用前缀」这种分裂也随之消失。
>
> | AAD 原本要绑 | 现在谁扛 |
> |---|---|
> | `sid`（防跨上传搬片） | **每次上传一把新 `k_body`**（§5.9 方案二）⇒ 别的上传的片根本解不开 |
> | `offset`（防搬位置） | ① `X-Pm-Mac` 签名覆盖 `offset`（改头即验签失败）；② 密文里的片序号必须接得上（§5.8） |
> | `len` | `X-Pm-Mac` 签名覆盖 `len` |
>
> ⇒ **别指望它防重放**（那是 §5.5 + 一个 `sid` 只落一个文件）；也**不用**为了「只有 XChaCha20 支持 aad」多写一条路径。完整论证见 §5.8。

**为什么不做「整个文件一次加密」**：NaCl 的 AEAD 是单次调用 API（没有流式接口），1GB 不能放内存；而按片加密与「按片校验、按片推进」天然对齐。

**片大小：15MB（决定）**，由服务端在 `upload_ready` 里下发（将来调参不用改手机页面）。

| 为什么是 15MB | |
|---|---|
| 为什么不能太小 | 吞吐 ≈ 片大小 ÷ 每片来回时间。相对现在的 256KB，15MB 把 RTT 部分摊销掉 **60 倍**（§1.2）——这是本次提速的主要来源 |
| 为什么不能太大 | Cloudflare 单请求 100MB 硬限，15MB 留了 6 倍余量；且片越大，服务端「整片收齐才能解密」占的内存越大（§6.3）。⚠️ **09-23 改**：「单片失败要重来多少」不再是理由——失败即放弃整个上传（§5.6.4），重来多少与片大小无关 |

即这是一个「**少等几个来回**」和「**内存占用 / CF 余量**」之间的取舍，15MB 是偏向少等的选择。

> ⚠️ 片大小的取舍与进度条**无关**：片内进度由服务端的 `upload_progress` 帧提供（§5.13），与片大小是两套独立节流。片大小只决定**内存占用**与**请求开销**，所以不必为了进度好看把片切得很碎。
>
> （09-23 修正：这里原文写的是「片内进度由浏览器的上传进度事件提供，几十 KB 粒度」—— 真机上那条在 CF 下是假的，见 §5.13。）

### 5.5 分片规则：靠 offset 幂等，不靠一次性票据 【规范】

**判定顺序固定为「验签 → offset 判定（下表）→ 解密」**（§5.8 前提 1），本表的「情况」列就是中间那一步。

服务端对每一片只做三种判定（`received` 是服务端手里那个「已确认落盘的字节数」）：

| 情况 | 判定 | 动作 |
|---|---|---|
| `offset == received` | 正常推进 | 验签 → 解密 → 写 `.part` → `received += len` → 200 |
| `offset + len <= received` | **重复片**（重放） | **不写盘、不报错、不作废**：回 200 + 当前 `received` |
| 其余（`offset > received`、部分重叠） | 错位（自家客户端发不出来） | **作废这次上传**（调 §5.6.3 的 `abort_session()`）+ 409 + 当前 `received` |

也就是说服务端对一片只有三个出口：**收下 / 忽略 / 作废**——没有「让客户端从 N 续传」这一支。**不做重传、不做续传**（§9-4）：出错就让用户重来。

这样「重放」与「错位」被干净地分开：

- **重放**（把录下的片再发一遍）→ 命中第二行 → 被忽略，产生不了任何新写入，也**不会被用来搞破坏**。⚠️ 这正是第二行**不能**写成「作废会话」的原因：LAN 下明文可嗅探，攻击者只要能录下一片，就能靠重放把别人正在传的上传打掉。⇒ **「忽略」是这一支唯一安全的答案。**
- **想往前写**就必须构造 `offset == received` 的请求，而那需要**合法签名**（§5.3）**并且**用本会话的 `k_body`、并且片序号正好接得上（§5.8）——三处都在拦。

配合 §2.3 的「一次性作用域 = 一个文件」，这形成一个完整的防护闭环：

| 攻击 | 被谁拦住 |
|---|---|
| 重放整个上传（把录下的所有片再发一遍） | 一个 `sid` 只落成一个文件；已收尾的偏移不会推进 |
| 重放单片 | 命中「重复片」，不写入 |
| 把某一片的密文搬到别的位置 | 密文里的片序号接不上 ⇒ AEAD 解密失败（若改的是头里的 offset，则先撞 `X-Pm-Mac`） |
| 拿到另一会话的片换 `sid` 用 | **每次上传一把新 `k_body`**（§5.9）⇒ 别的会话的片根本解不开 |
| 伪造/篡改片 | 头签名 + AEAD 认证标签 |
| 猜路径硬传 | 不知道随机 `sid`（24 字节，§4.2）；而且验签不过 ⇒ 不读 body、直接关、**不碰会话**（§5.2 的 ⚠️） |
| 拿别人的 `sid` 硬塞一片 | 签名（`k_mac` 是本会话专属的）+ 片序号接不上（用别的 `k_body` 加密的片也解不开） |

> 早先考虑的「整个请求一次性」被放弃了：它会让正常的重试也一起被拒，而且失败不可区分。防重放的粒度落在**片**上才分得清两者。

> **为什么不是把「严格相等」放宽成「单调递增」？** 递增确实能解掉「丢一片就整条死」，但会换来一个更糟的问题：**服务端会以为自己是连续的**。片 2 丢了、片 3 带着更大的号到了，单调判定会放它过去，`received` 直接从片 3 末尾算起 —— **文件中间那个洞再也没人知道**，最后交付一个损坏的文件。
>
> 所以判据不是「号更大了就收」，而是「**你是不是当前该写的那一段**」。这正是上面三行判定在做的事，也是它必须靠 `offset`、而不能靠「第几条」的原因。

### 5.6 收尾、取消、暂停、失败：什么时候需要「通知服务端」 【规范】

先把六种情形分开——它们常被混成一件：

| 客户端状态 | 要不要通知服务端 | 靠什么 |
|---|---|---|
| **传完了** | ❌ 不需要 | 最后一片的响应就是结果（服务端在返回前已经改名 / 写剪贴板） |
| **用户点了取消** | ✅ 需要 | **WS `upload_cancel` 帧**（§5.1）。⚠️ **不能指望 `xhr.abort()`** —— 实测证明服务端会照收不误，见 §5.6.1 |
| **某一片失败**（4xx / 5xx / 网络错） | ✅ 需要 | 客户端**放弃这次上传**并**发一帧 `upload_cancel`**（§5.6.4）。没有「重传当前片」这一支 |
| **WS 断了 / 页面关了** | ✅ 服务端自己就知道 | **WS 关闭 ⇒ 该连接名下所有上传会话立即作废**（§4.2 / §5.6.4），客户端什么都不用发 |
| **暂停**（切后台 / 锁屏） | ❌ 不发，但**不再被保留** | 什么都不做；WS 判死后与上一行同路（会话被作废）。这是 09-23 修订的代价，见 §5.6.4 |
| **进程被杀** | ❌ 发不出去 | **TTL 扫描**（降级为兜底：覆盖连接级作废看不到的场景，如服务端自己重启） |

⇒ 结论：**「通知服务端」的正确形态是「WS 连接级作废做主力 + `upload_cancel` 做主动撤销 + TTL 做兜底」，而不是设计一套通知协议。** 六种情形里真正需要客户端说话的只有「取消」和「放弃」两条，而且用的是**同一个** `upload_cancel` 帧。

**收尾（服务端自动）**：`received == size` 时：

- `file`：`.part` 改名去掉后缀，落到 `~/Downloads/PhoneMic/`（规则沿用 `wire-protocol.md` §9.9：重名改号、改名前再查一次重名）；
- `photo`：重组后的字节直接写系统剪贴板，**不落盘**；
- 然后才发 200 + `{"done": true, "saved": "…"}`。

取消走 **WS 帧 `upload_cancel`**（协议见 §5.1）。下面是「为什么」——这一节是 v3 的主要修订点。

#### 5.6.1 为什么 `xhr.abort()` 停不下服务端 【理由】

**实测现象（09-20）**：手机点取消、`xhr.abort()` 返回、UI 已显示取消，但**服务端仍在接收**，终端进度还在走。

三层原因，按确定性排：

1. **CF 是缓冲代理（主因，调参绕不过去）。** CF 模式下的上传是两段串联：手机 → CF 边缘（这段快，实测 6MB 用 6.82s），CF 边缘 → 隧道 → PC（这段是瓶颈）。客户端 `abort()` 断掉的是**第一段**，但 **CF 手里已经收下的字节仍然会吐给 origin** —— 它必须把 body 送完才敢收 origin 的响应。所以在 CF 下，abort 对 origin 侧「正在接收」几乎无影响。
2. **`ClientDisconnect` 在语义上不能拿来做取消。** 读 body 期间断连有两种原因（用户取消 / 网络抖动），服务端**分不出来**。v3 时这一条的理由是「必须假设客户端会回来重试」；09-23 已不做重试（§5.6.4），但**结论不变**：意图仍然分不出来，而且 CF 会把 body 吐完（上一条），等服务端看到断连时这一片早就被完整读走了。⇒ 取消只能靠一条**带外**信号，「从连接状态反推」这条路不成立。
3. **uvicorn 的断连检测有时机差。** 它只在**下一次 `receive()`** 时才返回 `http.disconnect`，也就是说「读到断连」这件事本身要等一次读循环；若此刻正卡在写盘或解密，还会更晚。

⇒ 结论：**需要一个「带外、明确、即时」的信号，而且这个信号不能走那条正在传 body 的连接。**

候选有三条：HTTP `DELETE`、WS 帧、TCP 断开。第三条已被上面第 2、3 点排除。前两条对比：

| | HTTP `DELETE /api/upload/<sid>` | **WS 帧 `upload_cancel`（采用）** |
|---|---|---|
| 能不能中断正在读 body 的 PUT | **两者都要**额外做「共享 abort 标志 + 读循环检查」——这一层省不掉 | 同左 |
| 走 CF 时的形态 | 要经过 CF 边缘；CF 对非 GET/POST 方法的行为、以及它到 origin 的连接复用都**不在承诺范围内，未验证** | **本项目已经在跑的通道**，行为已知（下行不限速，几 KB 的帧即刻可达） |
| 鉴权 | 要养一套 `k_mac` 签名 + 「验签先于副作用」+「`DELETE` 也要排空 body」三条约束（v2 的 §5.3 / §6.1） | **免费**：WS 握手时已经认证过 |
| 发起成本 | 取消要**另开一个 HTTP 请求**；iOS 切后台时新请求可能被挂起 | 在**常驻连接**上写一帧就走 |
| 归属 | 要靠 `sid` 自己去认 | **一对一**：一个连接只服务一台手机 ⇒ 连 `sid` 都只是「给日志看的」 |
| 回执 | 需要 `200` 才知道到了 | **不需要**：单向、幂等；失败也不致命（TTL 兜底） |

⇒ 所以取消不是「HTTP 换 WS」的偏好问题，而是：**`abort()` 那条路根本不通，而剩下能通的两条里，WS 帧每一条维度都更优。**

> 上面第 3 行那句「**两者都要额外做读循环检查**」值得单独强调：**换协议本身并不解决「服务端停不下来」**。真正让它停下来的机制是「会话里有个 abort 标记，PUT 的读循环每次收到数据就查一次」——WS 帧只是**把这个标记置位的那只手**，只不过它是所有候选里最快、最省事、且已经认证过的那只。

#### 5.6.2 「终止接收」的准确含义 【规范】

这一点要说透，否则会以为「发个帧，网卡就停了」：

| 能做到 | 做不到 |
|---|---|
| ✅ **立刻停止写盘**：读循环查标记 → 跳出 → 后续字节全部丢弃 | ❌ 让 CF 停止吐字节（缓冲在 CF 手里，见 5.6.1 主因 1） |
| ✅ **立刻关 `.part` 句柄、删掉半成品** | ❌ 让已经在路上的那 15MB 退回手机 |
| ✅ **作废会话**：摘除密钥，后续 PUT 一律 401 | ❌ 省下已经消耗掉的那点带宽 |

**「终止接收」的正确含义是「终止写入与交付」，不是「让网卡停下来」。** 而真正要紧的正是前者——用户点取消，要的是「这个文件不会出现在我的下载目录里」，不是「省流量」。所以这个方案是完足成立的，只是别拿「带宽」去衡量它。

#### 5.6.3 服务端实现形状 【规范】

上传会话记录里加一个 `abort_event`（`asyncio.Event`）与**会话所属的连接号**（`conn_id`），并复用 §6.3 那把**按 `sid` 的锁**。

**所有「作废」收敛到一个函数**，四个触发点（见 §5.6.4）：

```
abort_session(sid, reason):
    async with 锁(sid):                    ← 与 PUT 的写盘段共用同一把锁
        关 .part 句柄（容忍「已经关了」）
        删 .part
        从会话表摘掉密钥与记录
        abort_event.set()                  ← 在途的 PUT 读循环据此停写

WS 收到 {"type":"upload_cancel","sid":…} → abort_session(sid, "client")     ← 取不到会话即返回（幂等）
WS 关闭（本连接）                        → 遍历会话表，对每个 conn_id 匹配的会话 abort_session(sid, "ws_closed")
PUT 收尾成功                             → 不调它（改名落盘；会话留到过期，§4.2）
TTL 扫描                                 → abort_session(sid, "expired")

PUT handler 的读循环：
    async for chunk in request.stream():
        if abort_event.is_set(): break     ← 跳出；本块及之后一律不写盘
        async with 锁: 写 .part
    循环外：会话已作废 ⇒ 直接返回（客户端早已 abort，拿不到响应也无所谓）
```

四条实现约束（都是「写反了不报错、只在不常见路径上出事」的那类）：

1. **检查点在「写盘之前」，不是「下一片开始之前」。**否则取消时那一块的剩余部分还会落盘。
2. **「谁来删 `.part`」不能漏**。用户在**片与片的间隙**点取消时，根本没有在途 PUT ⇒ 「等 PUT 收尾时删」永远等不到。所以删除一律走 `abort_session()`（WS 帧 / WS 关闭 / TTL 三个触发点都在 WS 侧或后台侧），**PUT 路径只管跳出、不删**。
3. **删除必须等句柄关掉，且关句柄要容忍「已经关了」。**Windows 上打开的文件删不掉，而 PUT handler 可能正握着句柄写 —— 这就是上面用**同一把锁**把「写盘」与「作废」串起来的原因（锁只包住写盘那一小段，不是整片读循环）；PUT 侧退出时的 `close()` 也必须幂等。

4. **取消后不要「一跳出读循环就返回」，要「读完、丢弃」。** 若读循环一发现标记就 `break` 并立刻回响应，那条 TCP 上还剩 CF 正在吐的十几 MB 未读数据 ⇒ **照样触发 §6.1 的 RST**（RST 发给 CF，会让它那头报错甚至重试）。正确形状是把 `break` 换成「**不再写盘，但继续读**」：服务端读 CF 吐来的字节很快（实测 15.9MB/s），多花约 1 秒换连接干净收尾。**⇒ 也就是说，「服务端还在接收」这个观感在取消后仍会持续约 1 秒 —— 这是物理限制，绕不过去；但那一秒里它已经不再产出任何文件了。**

> ⚠️ `abort_event` 必须放在**会话表**里，不能挂在 WS 连接对象上：HTTP 请求和 WS 是**两个独立的 handler**，它们之间唯一的共享物就是会话表（§4.2）。这也顺带说明为什么 `upload_cancel` 的**准入**可以按连接做（一对一，连 `sid` 都不必校），而**状态**必须按 `sid` 存。

**`ClientDisconnect` 不等于取消。** 读 body 期间断连有两种完全不同的原因，而**单看这个断连**服务端分不出来：用户点了取消 / 关了页面（要删）；或只是网络抖了一下（地铁过隧道、切 WiFi）。⇒ 正确的形状是** PUT 这一侧什么都不做**：

- `ClientDisconnect` → **只丢弃当前这一片**（没收齐的半片不写盘），`.part` 与 `received` 原样保留；
- **删除只有三条路**，而且都走同一个 `abort_session()`：**收到 `upload_cancel`** / **WS 关闭** / **TTL 过期**（§5.6.4）。

> ✅ **「`upload_cancel` 帧 + WS 关闭」这个组合正好补上了「分不出来」**（§5.6.1 / §5.6.4）：客户端放弃上传时**一定**会发一帧（§5.6 那张表），WS 断了则由服务端自己作废——两条都是**显式**的。⇒ 断连本身只当「这一片作废」处理，不必再从连接状态猜意图。**这是取消走 WS 的第二个好处。**

TTL 因此在 09-23 之后**退居兜底**：连接级作废覆盖了绝大多数情况，TTL 只负责「连接还活着但谁也不动了」以及服务端自己重启这类边角。

#### 5.6.4 WS 断连即全取消；不做重传、不做续传 【理由】

**09-23 决定，三条一起：**

1. **WS 断连 ⇒ 该连接名下所有上传会话立即作废**（连接级作废成为主力，TTL 退为兜底）。一次上传本来就只活在一条连接里（几十秒到十几分钟），WS 是它的**控制面**；控制面没了，留着数据面只会攒下一堆「服务端还在等、客户端已经不打算传了」的半成品。三个好处：`.part` 不会没人管、密钥寿命自动收敛到连接寿命、服务端不必再从「多久没进展」去反推意图。
2. **不做重传**：任何一片失败（4xx / 5xx / 网络错）⇒ 客户端**放弃这次上传**并发一帧 `upload_cancel`，把具体原因提示给用户，重来由用户点（= 全新的 `sid` 与钥匙）。服务端侧对应 §5.5 的「三个出口」。
3. **不做跨中断续传**：`.part` 不写元信息、不记来源，也**不用「文件名 + 大小」去认「是不是同一个文件」**。

**为什么「文件名 + 大小」不能用来认领旧 `.part`：**

| 问题 | 说明 |
|---|---|
| 它是**客户端自报**的 | 服务端没有任何办法验证「这个 `.part` 的前半段真的是这个文件的前半段」。把上报的字节当成前缀接上去，等于允许往一个已有文件里拼任意内容 |
| 它打破 §2.3 的约束 | 「一个 `sid` 只落成一个文件」之所以成立，靠的是落盘名、`size`、`offset` 在 ① 就钉死。允许「认领旧 `.part`」= 开了一个**跨会话**的写入口 |
| 正确的形态很贵 | 真要做得靠「已完成字节数 = `.part` 的字节数」当锚点，再加「服务端在 ① 下发一个随机校验值、客户端重传时带上」之类的绑定 ⇒ 直接升级成一套断点续传协议，与「不做可靠性」（§9-4）冲突 |

**代价（认账）**：CF 档按 120KB/s 算，100MB 重传一次 ≈ 14 分钟；切后台超过 WS 判死窗口（~60s）也会被取消。⇒ 所以**提示必须说清原因**（§5.12）——用户能分辨「我点的取消」和「连接断了」，才谈得上「重来一次」。

> **配套且不能漏**：① §6.5 的「HTTP 活动也刷新 WS 判活」从建议升为必做，否则一条健康的大片上传会在 60 秒时自杀；② §6.2 要放行 `/api/upload/`；③ WS 关闭时的清理必须只作用于**本连接**名下的会话（一个连接只服务一台手机，§5.6.1）。

### 5.7 大小上限 【规范】

| 类型 | 上限 | 在哪拦 |
|---|---|---|
| `photo` | 32MB（初值） | `upload_begin` 阶段就拒（全程在内存，必须防内存炸弹） |
| `file` | 由服务端配置，v1 可不设 | 同上 |

在 ① 阶段拦，意味着**一个字节都还没传就被拒绝**，比现在传到一半才失败好。

### 5.8 与现有加密层的接口：什么都不用改 【理由】

这一节回答「现有加密算法把防重放 seq 直接包装在里面，改 HTTP 上传是不是要把实现拆一遍」。

**结论（09-23 定）：不用拆，`CryptoProvider` 的接口一个字不改。** 上传片直接调现有的 `encrypt()` / `decrypt()`，但**用的是以 `k_body` 单独创建的另一个实例**（理由见下）。provider 内部那个 seq 计数器**恰好就是上传需要的那个判据**——在独立实例里它就是**片索引**。下面是「为什么能用」以及「靠哪三件事撑着」。

#### 先把 seq 是什么讲清楚 【背景】

`base.py` 的接口只有两个方法，`seq` 完全在 provider 内部，调用方看不见、也插不进去：

```python
encrypt(plaintext) -> bytes      # xchacha20.py: aad = self._tx_seq.to_bytes(8, "big")
decrypt(ciphertext) -> bytes     # 解密要求 self._rx_seq 严格相等，不等即 MAC 失败
```

它承载的语义只有一句：**「这是我发出的第 N 条」**。接收方拿「我期待的第几条」去比对，对不上就拒。

⇒ 于是它隐含两个条件：

| 条件 | 为什么 |
|---|---|
| 同一条加密流上 seq **不重、不漏** | 「第几条」是拿 tag 一起算的，双方必须一致才解得开 |
| 接收方**按顺序**消费 | 接收方的期待值是一个单点（N+1），跳号就永久错位 |

WS 恰好两条都满足（TCP 保证顺序，丢了就断连），所以它工作得很好。

#### 为什么必须是另一个实例 【规范】

`encrypt()` / `decrypt()` 只在**一条**流上成立：seq 是**单个**计数器（§7 的表里也写着「同一实例不允许被两条流交叉使用」）。而上传引入的是**第二条物理通道**：客户端调用 `encrypt()` 的顺序是「WS 帧 / 上传片」交错的，但这批字节**到达服务端的顺序由两条独立 TCP 连接各自决定**，谁先到不由客户端说了算。

只要客户端在上传期间发过**任何一条**上行 WS 帧（`upload_cancel`、用户正在打字、鼠标动作……），两条流就会交错，服务端按到达顺序解密时**必有一条解不开**：

| 服务端先收到 | 后果 |
|---|---|
| 上传片（seq 比那条 WS 帧大） | 片解密失败 ⇒ **整条上传被作废**（§5.6.4「失败即放弃」） |
| WS 帧（seq 比上传片大） | 帧被当「不可用帧」丢弃（`unwrap()` → `None`）⇒ **静默丢一次操作** |

两个方向都是**概率性**失败（取决于网络调度），比确定失败更难查。

⇒ 上传侧用一个**独立的 Provider 实例**：

| | 跑 WS 那个实例 | 上传这个实例 |
|---|---|---|
| 密钥 | 会话密钥（ECDH 结果） | `k_body`（每次上传新生成，§5.9 方案二） |
| 算法 | 协商结果 | **同一个**协商结果（`SecureSession.negotiated_algorithm`） |
| seq 语义 | 第几条 WS 帧 | **片索引**（0、1、2…） |
| 顺序靠谁保证 | TCP（WS 是唯一通道） | 客户端逐片 PUT、收到 200 才发下一片（§3） |
| 生命周期 | 连接 | 上传会话（与 `.part` 同生共死） |

两侧**都不需要改接口**：Python 侧直接 `create_provider(algo, k_body)`（现成的工厂函数）；**JS 侧要给两个 Provider 加一个「注入密钥」的入口**——现有 provider 的密钥是内部 ECDH 派生的（`_deriveSharedKey()`），没有外部入口，必须新增（落点见 §7）。

#### 为什么上传直接复用它是可行的 【理由】

**09-23 之前的设计**是给 provider 加 `encrypt_with(pt, ctx)` / `decrypt_with(ct, ctx)`，把 `ctx = sid ‖ offset ‖ len` 当 aad（或明文前缀）传进去，理由是「丢一片之后 seq 就永久错位、整条上传死掉」。

**这个理由现在不成立了**，因为一条政策变了（§5.6.4 决定「失败即放弃」）：

| | 旧前提 | 09-23 之后 |
|---|---|---|
| 片丢了怎么办 | 要能补（重传 / 续传）⇒ 判据不能只是「连续」，得是「第几字节」 | **放弃整条上传** ⇒ 「补洞」这个需求不存在 ⇒ 「seq 永久错位」这个病也不存在 |
| 重放一片会怎样 | 会让 seq 对不上 ⇒ 被当成解密失败 | **它根本走不到解密**，见下 |

服务端的判定顺序是固定的三步（§3 / §5.5）：

```
验签（X-Pm-Mac）  →  offset 判定（三行）  →  解密
```

重复片（`offset + len <= received`）在**第二步**就被判成「忽略」、直接回 200，**压根不会进 `decrypt()`**。所以 provider 那句「seq 必须严格相等」在重复片上不会被触发 —— 不是它失效了，是它没有机会生效。

⇒ 「丢一片就整条死」描述的是一种**在「失败即放弃」政策下不会发生**的场景。

#### 三个必须同时成立的前提 【规范】

上面能成立，靠的是下面三件事。**缺一件就不是「简化」，而是漏**：

1. **判定顺序必须是「验签 → offset 判定 → 解密」，不能颠倒。** 这是**正确性依赖**，不是性能顺序：只有让重复片 / 错位片在解密之前被拦下，provider 的 seq 才永远接得上。⚠️ **写反了不报错**，只在「有人重放一片」时静默变成「解密失败 ⇒ 关连接」，比「忽略」差一档（与 §5.2 那条 ⚠️ 的红线同源）。
2. **每次上传一把新 `k_body`**（§5.9 方案二）。provider 的 seq **不携带「属于哪次上传」**的信息，会话隔离完全靠钥匙：换了钥匙，别的上传的片根本解不开。⇒ 这把新钥匙在这里**不是可选优化，是会话隔离的唯一来源**。
3. **同一把 `k_body` 只服务一个上传会话**（⇒ 上传实例与 `.part` 一样是会话私有的），且**每片只加密一次**（seq 单向递增）。服务端侧对称：**那个实例的** `_rx_seq` 必须与 `received` 同步推进。

⚠️ **第 3 条带一个实现陷阱，写反了会很难查**：`decrypt()` 一旦成功，provider 的 `_rx_seq` 就**前进且不可回退**（接口没有「撤销」这个动作）。所以 **「解密成功但写盘失败」不能靠回退 `received` 重来** —— 那会让 `_rx_seq` 与 `received` 永久错位，**后面每一片都解不开**。正确做法：**写盘失败即作废会话**（`abort_session`，§5.6.3），与「失败即放弃」一致。

#### 为什么不留一个更灵活的入口 【理由】

「给 provider 加个能传 ctx 的入口」听起来只是多一个方法，实则连着带来三样东西：接口变两份（旧方法退化成薄包装）、JS 侧再镜像一遍、以及**两条实现路径**（`crypto_box_easy_afternm` 没有 aad 参数，所以 XSalsa20 无论如何都得走前缀）。而它换来的能力（把任意元数据焊进认证范围）**在上传侧已经被别的机制覆盖**：

| 想绑住的东西 | 靠谁 |
|---|---|
| 这一片属于哪次上传 | 每次上传一把新 `k_body`（§5.9） |
| 这一片该写在哪个位置 | ① `X-Pm-Mac` 覆盖 `offset`（改头即验签失败）；② 密文里的片序号必须接得上 |
| 这一片有多少字节 | `X-Pm-Mac` 覆盖 `len` |

⇒ **不采用。** 顺带一个好处：§5.9 那张表里「方案一要让 `e2ee.py` 暴露 `session_key`」的麻烦，也就没有存在理由了。

#### 顺带：两种算法现在还差在哪 【规范】

统一之后，两个 provider 的**机制完全一样**，只有底层原语不同：

| | XSalsa20（Box） | XChaCha20（AEAD） |
|---|---|---|
| 片序号放哪 | 明文前 8 字节（`crypto_box_easy_afternm` 没有 aad 参数） | ~~aad~~ ⇒ **也改成明文前 8 字节**（09-23 统一） |
| 统一的好处 | 一条实现路径、一组测试；`+8` 字节开销两种算法一致 ⇒ `Content-Length` 仍可精确预计算 | 同左；调用方**零感知**（不用传 ctx、不用挑算法分支） |

> ⚠️ **这是一处 `crypto/` 的真实改动**（XChaCha20 从「用 aad」改成「拼前缀」）。它换来的是**接口不动**——净起来是变简单：加接口那个方案要改 `base.py` + 两个 provider + JS 侧；这个方案只改 XChaCha20 那个 provider 的**内部几行**，`nacl_box.py` 一个字不动。落点见 §7。

#### 附：上传这一侧到底还需不需要「防重放」 【理由】

不需要，而且这不是妥协 —— 这三件事本来就不该由一个计数器全包：

| 东西 | 干什么 | 谁提供 |
|---|---|---|
| **nonce**（AEAD 的随机数） | 同样的明文 + 同样的密钥，每次密文都不一样 | 本来就有：每片 `randombytes_buf`。它是**发送方单方面**的，不需要双方约定，**也不防重放** —— 重放者连密文一起重放，nonce 一模一样，一样合法 |
| **片序号（seq）** | 让接收方能判断「这条是不是我期望的下一条」 | provider 内部，8 字节前缀（本节） |
| **防重放**（判断「这条我以前见过没有」） | 拒绝重复的那一片 | 上传靠**偏移幂等**（§5.5）+ **一个 `sid` 只落一个文件**（§2.3）；WS 靠 seq |

所以「每次发个随机数就行」这个直觉里，**随机数那一半已经在用了（nonce）**，只是它管的是「密文不可预测」，不是「重放」。用它去顶替片序号也不行：**随机数不携带位置信息**，「这一片该写在哪」就无处可挂。

顺带澄清一个容易合并的点：**把 offset 放进 HTTP 头（`X-Pm-Offset`）不等于它进了密文。**

| 放哪 | 作用 | 什么时候起作用 |
|---|---|---|
| HTTP 头 | **读 body 之前的门禁**（§5.3 的签名覆盖它） | 明显不属于我们的请求，**0 字节**就被拒 |
| 密文里的片序号 | **让密文搬不走**（§5.4） | 搬到别的位置，序号接不上 ⇒ 解密失败 |

**两份都要，各管一件事。** 至于头部的字节开销：`X-Pm-Offset: 31457280` 约 20 字节，对面是 15MB 的 body，比例 10⁻⁶ 量级 —— **不值得为省这几个字节牺牲绑定**。

#### 结论 【规范】

**不用把加密实现拆两份，也不用加接口。** 上传片直接走现有 `encrypt()` / `decrypt()`，前提是上面那三条（判定顺序 / 每次一把新 `k_body` / 一把钥匙只服务一次上传）。WS 路径连行为都不变（现有加解密用例应当全绿）。需要动的文件见 §7。

### 5.9 上传密钥从哪来：派生，还是每次上传新协商一把 【理由】

**这一节和 §5.8 是两个互相独立的决定**，不能互相代替：

| 决定 | 选项 | 不解决会怎样 |
|---|---|---|
| **A. 加解密走哪条路**（§5.8） | 直接用现有 `encrypt()`（**09-23 已定**）/ 给 provider 加 ctx 入参 | 重复片会被当成「解密失败」而不是「忽略」（**必须解决**；已由「offset 判定前置」解决） |
| **B. 钥匙从哪来**（本节） | 从 `session_key` 派生 / 每次上传新协商 | 两套协议共用一把钥匙（**可选**，而且它解决不了 A） |

两种钥匙来源都可行：

**方案一：从 `session_key` 派生**（`BLAKE2b(session_key, label="pm-upload-v1", digest_size=64)` → 切 `k_mac` / `k_body`）。好处是不用传密钥；代价是要改 `e2ee.py` 把 `session_key` 暴露出来，且同一页面会话内的所有上传共用一族钥匙。

**方案二（09-23 已定）：每次上传新协商一把一次性钥匙**

1. `upload_begin` 时服务端 `secrets.token_bytes(64)`，切两把（`k_mac` / `k_body`），写进上传会话记录；**并用 `k_body` 建一个上传专用的 Provider 实例**（§5.8「为什么必须是另一个实例」）；
2. 在 `upload_ready` 里把这两把带下去 —— **走的是现有 WS 帧，本来就被 `session.wrap()` 加密着**，不需要任何新的密钥交换；
3. 收尾 / 过期 / 取消时，连同会话记录一起丢掉。

| | 方案一 派生 | 方案二 每次新协商 |
|---|---|---|
| `e2ee.py` | 要改（暴露 `session_key`） | **一个字不用改** |
| 密钥怎么到客户端 | 不用传 | 走现有 WS 帧（已被加密保护） |
| 一次泄露的爆炸半径 | 该页面会话内的**所有**上传 | **只有这一次上传** |
| 「用完就消掉」 | 概念上可以，但 `session_key` 还在 ⇒ 历史密文仍可解 | **真的没了**：事后 `session_key` 泄了也解不开历史上传的密文 |
| 实现量 | 一次哈希 + 暴露一个字段 | 一次 CSPRNG + 多传两个字段 |

**采用方案二**（09-23 最终确认）。四条理由：① **不动 `e2ee.py`**（少一个共享文件的回归面）；② **每次上传独立的机密性**（一次泄露的爆炸半径就是这一次上传）；③ **概念直白**（不用解释 KDF 标签）；④ **连派生都省了**（`secrets.token_bytes(64)` 直接切两把）。

⚠️ **方案二要多做三件事，少一件都不算完成**

1. **「销毁」要真的实现**：收尾 / 过期 / 取消 / 进程退出，四条路径都要把密钥从会话记录里摘掉。但**别把它当安全属性卖** —— CPython 无法可靠擦除内存，「销毁」的密码学意义主要来自**不再持有**（从表里删掉、任何路径都取不到），而不是把内存擦干净。当卫生习惯就好，别当防线。
2. **别进日志**：`upload_ready` 帧如果被 trace 日志打印（`PHONEMIC_LOG=trace` 那条路径），钥匙就落盘了。要配一条「含 key 的帧不打印」的规矩。
3. **客户端只在内存里持有**：不进 localStorage。（§9-4 已定**不做**跨中断续传，所以这条不会有例外；将来真要做，也必须**重新协商一把新钥匙**，而不是把旧钥匙存下来。）

> ⚠️ 上面这三条是**方案二专属**的卫生要求。它们只在改走 ECDH 取钥匙时才会失效（密钥不过线 ⇒ 前两条自然消失）——而方案三已于 09-23 否决（见下），所以**三条都要做满**。

⚠️ **方案二的定位在 09-23 被抬高了：它不是「顺手做的优化」，而是会话隔离的唯一来源。** §5.8 决定不给 provider 加 ctx 入参之后，上传片与上传会话之间**不再有任何密码学关联**（片里只有「这是第几条」，没有「这是哪一次上传」）——把不同上传隔开的**只有钥匙**。⇒「每次上传一把新 `k_body`」这一条从「更好」升级为「**必须**」：缺了它，另一个会话的片就能被搬到本会话继续用（§5.8 前提 2、§5.4 那张表第一行）。

#### 方案三（09-23 提出，**已否决**）：每次上传新做一次 ECDH 【理由】

**09-23 拍板：不采用，保持方案二。** 曾考虑让手机端每次上传现造一对 X25519 临时密钥（`new`），只把公钥交上去、两边各算一次 ECDH 得到同一把 `shared`，再 `k_mac ‖ k_body = BLAKE2b(shared, …)`。它的收益是**密钥从不过线**（顺带让上面方案二的卫生要求 ①② 自然消失）。

**没有采纳**：收益是「密钥不过线」，代价是 `upload_begin` 多一个 `pub` 字段（协议面变更）+ 手机端多一条密钥对生成路径——是这两者的取舍。

> 附带的三条分析结论（`new.pub` **必须**走 WS 而不能放 PUT 头、「每片一把新密钥」不行、X25519 不能签名）讲的是「客户端自报公钥」这一类做法，与方案二已无关系，已移到 `MEMORY-detail.md` §12 留存，免得以后重走一遍。

### 5.10 能不能「提前终止」：三个检查点，只有一个做不到 【理由】

问题：**片有 15MB，服务端能不能先看一眼「你是不是合法的」，不合法就提前终止、别读完这 15MB？**

先把「提前」拆成三个可能的检查点，逐个看：

| # | 检查点 | 最早什么时候能判 | 现状 |
|---|---|---|---|
| ① | **这次上传本身该不该接受**（大小上限、`ref` 类型、磁盘余量） | `upload_begin` 之后，**一个 body 字节都没传** | ✅ 已做（§5.1 拒绝帧 + §5.7） |
| ② | **这个 HTTP 请求是不是我的**（`sid` / 长度自洽 / MAC 验签） | **读完头、还没读 body** | ✅ 已做（§5.2 / §5.3） |
| ③ | **这一片密文是不是合法** | ❌ **必须读完整片** | 做了，但做不到更早 |

①② 都在**零字节时刻**完成——这就是「提前」的全部可用空间，已经用满了。真正做不到的是 ③，原因是硬的，不是实现偷懒：

```
密文片 = nonce(24) ‖ 密文(n) ‖ tag(16)
                              ↑ 认证标签在最后 16 字节
```

没有 tag 就无法判断前面那 n 个字节有没有被改；而**两端的密码学库都只提供一次性（one-shot）接口**（已核实：PyNaCl 的 `nacl.bindings.crypto_aead` 只有 `encrypt` / `decrypt`；`sodium.js` 同样）⇒ **要么整片收齐，要么不判**。

所以「读了文件头几字节就判断合法」在密码学上不成立，除非把片切小——而**片小正是现在慢的根源**（§1.2）。⇒ **「提前判断」与「15MB 大片」是直接互斥的两个诉求**，这是本轮唯一需要认账的代价。

两条绕路都不推荐：

- **换流式 AEAD**（libsodium 的 `crypto_secretstream_xchacha20poly1305`，本身就是为流设计的）：能把内存从 15MB 降到几十 KB，但**「能提前判」依然不成立**——secretstream 也是每块带 tag，能提前的前提就是块足够小，而块小=片小=回到慢。另外 PyNaCl 没有绑定它，服务端得自己写 ctypes。
- **每片再切小块各自加密**：等价于把片大小改回几百 KB，直接抵消本次提速。

> **边界要说清**：如果你说的「检查文件头」指的是**文件魔数 / 扩展名**（判断"这到底是不是一张图"），那更不该去 body 里嗅探——服务端读完第一片才知道，而它只是个 UX 提示、不是安全判据。要提前知道，正确做法是**在 ① 阶段让客户端声明**（`name` 已经在传了），用声明代替嗅探。

#### 「提前终止」到底能省什么 【理由】

**(a) 服务端已经决定拒绝（401 / 409 / 413），能不能干脆不读这 15MB？**

机制上能（返回响应后直接关连接、不碰 `request.stream()`），但**代价是客户端拿不到那个状态码**：服务端在接收缓冲还有未读数据时关连接会发 RST（§6.1），把客户端「已到达但还没读走」的响应一起丢掉 ⇒ 客户端看到的是一次网络错误，**分不清「我签名错了」和「网断了」**。

所以这件事**不能一刀切**，而是按「这个请求能不能拿出凭证」分两类——见下面「09-20 决定」那一节。

**(b) 那省下来的到底有多少？——已经封顶在一片**

因为**客户端是串行的**（§6.6：一次只有一个在途片），而且**任何失败都直接放弃这次上传**（§5.6.4）。所以一次会话里**最多白白传一片 = 15MB，而且只发生一次**。

按 09-20 的分类规则（下节）再看一遍，这个上限还能细分：

| 拒绝原因 | 旧规则 | 09-20 新规则 |
|---|---|---|
| **拿不出凭证**（MAC 验证失败 / 会话不存在） | 白读一片 15MB | **0 字节**——不读 body、直接关连接 |
| **自己人但状态不对**（400 / 409 / 413） | 排空一片 15MB | 仍是 15MB（客户端必须读到状态码才能自我纠正） |

#### 09-20 决定：拒绝时按「能不能拿出凭证」分两类 【规范】

| 情况 | 判据 | 怎么处理 | 为什么 |
|---|---|---|---|
| **拿不出凭证** | MAC 验证失败 / 会话不存在 / 已过期 | **不读 body、直接关连接**（顺手回 401 也行，收不收得到随缘） | 合法客户端**永远不会**落到这一支——它的签名必然是对的 ⇒ 对面一定不是自己人，不用客气 |
| **是自己人，但状态不对** | 签名对得上，但长度自相矛盾（400）/ 偏移错位（409）/ 超限（413） | **把 body 收完，再回 400 / 409 / 413，并作废这次上传**（§5.5） | 这是自家客户端，它需要**读到状态码**才知道该给用户提示什么 |

一句话：**分类边界就是信任边界**——「礼貌」只花在绝不可能是攻击者的请求上。

> ⚠️ **这条决定推翻了本文件早先的「保持一条规则」**（v3 及之前写的是「所有拒绝都排空」）。推翻了不等于旧论证是错的，而是它**失去了对象**：旧论证反对的是「**要区分**过期会话和陌生乱请求」（理由：会话被清掉时 `k_mac` 一起销毁、服务端根本没法验签，除非给过期会话留一段墓碑），而新规则**根本不区分**——两者都属于「拿不出凭证」，都直接关。墓碑表的顾虑随之消失。
>
> 代价认账：**过期客户端的 401 会被 RST 吃掉**，它只能看到网络错误 ⇒ 但对它来说这没差别：**失败就是放弃 + 提示**（§5.6.4），不需要认出具体原因。

**两个必须一起记住的后果：**

1. **半吊子排空 = 白做**。「关连接时接收缓冲还有未读数据」是 RST 的**充要条件** ⇒ 只读 64KB 却丢下 15MB，照样 RST、对方照样收不到响应。**要么读干净、要么一个字节不读**，中间那种「读一点表示礼貌」在机制上没有任何收益。⇒ 也说明 §6.1 里那个 64KB 的旧上限对上传端点**没有意义**。
2. **客户端不再需要「连续失败 N 次 ⇒ 重新协商」这条规则了**（09-23 简化）：不存在重传，任何失败都走同一个出口——**放弃这次上传 + 提示用户**（§5.6.4），下一次由用户重新发起，天然就是一次全新协商。「电脑重启后的第一次上传」会失败一次，用户看到提示再点一次即可。⇒ 这也顺带说明为什么「客户端分不清 RST 与真 401」不再是问题：**分不清也无所谓，两条路的处理完全一样。**

#### 一个白拿的例外：`Expect: 100-continue`（只对 `curl` 有效） 【理由】

**手机端用不了，这点是硬的**：`Expect` 在 Fetch 规范里是**禁止由脚本设置的请求头**，JS 设不了（`setRequestHeader` 会被忽略），浏览器自己也从不发（MDN 明确写着 "None of the more common browsers send the Expect header"）。⇒ 不能作为设计依据。

**但手工验证阶段白拿**：uvicorn 只在**应用第一次调用 `receive()`** 时才写 `HTTP/1.1 100 Continue`（`httptools_impl.py` 的 `RequestResponseCycle.receive()`、`h11_impl.py` 同构）⇒ 我们的 401 分支只要不碰 `receive()`，`curl -T`（默认对 >1KB 的 body 自动加 `Expect`）就会**一个 body 字节都不发**地拿到 401，且此时连接干净关闭（客户端没发 body ⇒ 没有未读数据 ⇒ 不会 RST）。可以直接拿它当 §10 阶段 2 的验证手法。

### 5.11 「路径被窃听」之后还剩多少暴露面（LAN 上没有 TLS） 【背景】

这一节回答一个具体担心：**局域网里有人抓包看到 URL，能不能拿着那个路径去「取消」别人正在传的文件？同理，日志端点是不是一个能刷爆硬盘的洞？**

（v2 原文问的是「伪造 HTTP `DELETE`」，v3 已把该端点整个删掉、取消改走 WS 帧——见 §5.6.1。下面按现行设计重述。）

#### 5.11.1 先给结论 【背景】

| 担心 | 结论 | 依据 |
|---|---|---|
| 窃听到路径 ⇒ 伪造取消（WS 帧 `upload_cancel`）毁掉正在进行的上传 | **不能** | 取消走 **WS 帧**（§5.6.1），得先把 WS 握上手；而握手需要 PC 公钥，公钥只在 URL fragment 里、浏览器从不外发（§5.11.2）⇒ 被动嗅探者连帧都发不出来。`upload_cancel` 本身是**单向、不带鉴权字段**的设计（§5.1），它的安全性完整地由「进得来这条已认证的 WS」承担 |
| 窃听到路径 ⇒ 灌日志把硬盘写死 | **不成立** | `_receive_client_log` 只往 `logging` 打；全项目日志只有 `StreamHandler`（控制台），**没有任何文件 handler ⇒ 不落盘**；打包版这个端点直接 404（页面侧也不启动日志模块）；单请求上限 256KB、单请求条数也有上限 |
| 窃听到路径 ⇒ 冒充手机连上 WS | **被动嗅探：不能**（5.11.2）；**能改包：能**（5.11.4） | 握手要 PC 公钥，而公钥只走 URL fragment |

所以这两条担心的落点是：**一条被 WS 握手挡住了，一条根本不落盘。** 但这条链路上确实有个真缺口——只是不在你指的位置（5.11.5）。

#### 5.11.2 一个关键事实：`#fragment` 永远不会出现在请求里 【背景】

加密模式的 PC 公钥是通过 **URL fragment** 传的（`#k=…&a=…`，见 `mobile.html::_parseUrlFragment`）。而**浏览器从不把 fragment 发给服务端**。这一点在整个威胁模型里很关键：

（`e2ee.py::append_to_url` 现在的形状就是这条规则的实物：`auth_method == "tofu"` 直接返回**裸 URL**、连 fragment 都不带；只有 `url_fragment` 才拼 `#k=<公钥>&a=<算法表>`。没有任何 token 分支。）

- 抓包的人能看到 `/xxxxxxxx/ws`、`/xxxxxxxx/api/lang.json`，**看不到 `/xxxxxxxx/#k=…`**；
- `api.py` 里**没有任何端点会返回公钥**——是「没有出口」，不是「有出口但被挡」。

⇒ **被动嗅探者手上只有 `secret_path`，没有公钥。** 这种状态下每条端点的实际可达性：

| 端点 | 真正的凭证 | 只有路径的人 |
|---|---|---|
| `GET /{secret}/`、`*.js`、`/api/lang.json`、`/api/keepalive` | `secret_path` | ✅ 能拉（只读，改不了状态） |
| `WS /{secret}/ws` | `secret_path` **+ PC 公钥** | ❌ 做不出合法的 `auth` 帧（`crypto_box_seal` 需要公钥） |
| `PUT /api/upload/<sid>` | `k_mac` | ❌ 401 |
| WS 上的 `upload_cancel` 帧 | **WS 握手**（需公钥） | ❌ 连不上 WS，就发不出这一帧 |
| `POST /api/client-log` | **只有路径** | ⚠️ 能（5.11.5） |

> 一句话：**路径泄漏的上限是「读页面 + 刷日志」，不是「冒充手机、取消你的上传、删你文件」。**

#### 5.11.3 一条现成的事实：TOFU 模式下没有 `secret_path` 【背景】

**明文模式已经不存在了**（§5.3），所以 v3 这里那整节「`none` 模式是个完全开放的局域网桥」失去了对象。但**它的技术前提没有全部消失**，这一点必须留着看：

`SecureChannel.__init__` 只在 `auth_method == "url_fragment"` 时生成随机入口路径；**`auth_method == "tofu"` 下 `secret_path` 是空串**（`append_to_url` 也直接返回裸 URL，手机拿到的是 `http://<ip>:12000/`）。而 `_normalize_path` 在 `secret` 为空时走的是**字面量白名单**（`_PUBLIC_PATHS`）。

⇒ 于是 TOFU + 局域网下，页面在 `/`、端点就是 `/ws`、`/api/client-log`、**`/api/upload/<sid>`**——**路径不是秘密，也不充当门禁**。这不是遗留缺陷，而是两套认证方式的分工：

| 认证方式 | 用在哪 | 入口怎么保护 | 上传怎么保护 |
|---|---|---|---|
| `url_fragment`（扫码） | CF / 跨网 | `secret_path` 做**防扫描**（+ 公钥只放在 fragment 里） | `k_mac`（§5.3） |
| `tofu`（手动审批） | 局域网 | **审批机制**（`sealed` 帧指派识别码 + PC 侧点确认），路径本身不设防 | `k_mac`（§5.3） |

**所以「上传 URL 不带页面前缀」（§5.2）不引入新的暴露面**：TOFU 模式下它本来就没有前缀；`url_fragment` 模式下它靠的是 `k_mac` 而不是路径——这恰好是 §5.11.5 那条规则要求的形态。

#### 5.11.4 诚实的天花板（已外移） 【背景】

5.11.2 那条「拿不到公钥」**只挡被动嗅探**。能改包的人可以在明文页面里插一段 JS 偷走 `#fragment`，从而完整冒充手机（握手、打字、上传）。

这不是本次设计引入的问题，而是「**在明文 HTTP 上做浏览器端 E2EE**」本身的边界 ⇒ **整段已移入 `docs/crypto-design.md` §2「威胁模型与信任模型」**，不在这里重复。

#### 5.11.5 真正的缺口：`client-log` 是唯一「有副作用却零认证」的端点 【背景】

顺手核了一遍，全项目**只有这一个**：

| 端点 | 会改变服务端状态吗 | 认证 |
|---|---|---|
| 页面 / JS / `lang.json` / `keepalive` | 不会 | 路径（够用） |
| `PUT /api/upload/<sid>` | 会 | `k_mac` ✅ |
| WS `upload_cancel`（§5.6.1） | **会**（作废会话、删 `.part`） | **WS 握手** ✅ —— 天然符合下面那条规则，不需要额外设计 |
| `WS`（键盘、剪贴板…） | 会 | 握手 ✅ |
| **`POST /api/client-log`** | **会**：每条都进控制台，每次最多 256KB 的 `json.loads` | **只有路径** ⚠️ |

它的注释里写着「能拿到 `secret_path` 就已具备访问资格」——**这条假设在明文信道下不成立**：路径是**每条请求都明文广播一次**的东西，抓包的人必然拿到。

实际后果是**控制台泛洪 + CPU**（不是磁盘）。而且它还有一个现成的暴露面：**TOFU + 局域网下路径就是字面量 `/api/client-log`（§5.11.3），连嗅探都不需要**。

**要提炼成一条规则：**

> **路径只提供「防扫描」（降低暴露面），不提供「授权」。**
> **凡是会改变服务端状态的端点，都必须自带独立认证。**

按这条规则，`POST /api/client-log` 需要补一道门。三个选项：

| 选项 | 做法 | 代价 | 挡得住谁 |
|---|---|---|---|
| **A. 只加限流**（推荐 v1） | 每 IP 每分钟 N 次 + 全局 QPS 上限，超限回 429（仍按 §6.1 统一排空） | 几十行，不改协议 | 挡住「刷」，不挡「知道路径就发几条」 |
| B. 挪进 WS | 日志当普通帧回传，服务端要求「必须先完成握手」 | 丢掉 `sendBeacon`（页面卸载前那几条日志）；要改 WS 协议与页面里的转发路径 | 被动嗅探者（他没公钥，握不了手） |
| C. 用协商密钥签名 | 复用 §5.3，头里带 `mac = BLAKE2b(k_log, "LOG\n" + len)` | 握手时得多下发一把 `k_log`；握手完成前的日志要排队或丢 | 同 B，但保留 HTTP 形态 |

**建议 A**，理由不是「A 最好」，而是**优先级**：打包版根本没有这个端点（`is_frozen()` → 404），所以这是**开发模式的洞，不是发布版的洞**，不该和上传主线抢工期。将来它若要进发布版，必须先做 B 或 C，不能再只靠路径。

### 5.12 出事了怎么告诉用户 【规范】

**决定：结果通知不新增下行帧，由客户端本地渲染**（09-23）。⚠️ 注意区分：09-23 之后确实新增了一条下行帧 `upload_progress`（§5.13），但那**不是通知** —— 通知是「一次性事件」，进度是「周期性状态」，两者不冲突；本节说的「不加帧」只针对结果通知。上传的成败客户端**自己就知道**——最后一片的 200、任何一片的 4xx/5xx、网络错误、WS 关闭，全都在它手上（WS 关闭那条，服务端也是各干各的、不需要告知）。所以这只是**界面表达**，不需要协议支持。

**不引入「电脑说」那一侧**（09-23 拍板）。上传结果**全部走现有的右侧气泡**（`addMessage` / `addFileMessage` 那一族），不做左侧样式、不加「电脑」标识。理由：上传是**用户自己发起的动作**，结果是对这个动作的反馈——它本来就是「用户说」的消息；硬说成「电脑说」反而把因果讲反了，还会让人以为电脑主动找上门。左侧留白，只给将来**真正的** PC 主动消息（电脑发文件 / 电脑通知），那时「谁在说话」才有区别。

三条约束：

1. **文案必须走 i18n 键**（`bubble_*` 那一族，**4 个语言包同步**）。⚠️ **不要**直接把 `upload_error.msg` 显示出来——那句话是英文调试串，而且语言跟着电脑走，与手机界面不一致（§5.1）。
2. **原因必须具体**（因为不做重传，用户只能靠这句话判断下一步）：区分「你点的取消」「连接断开」「会话已过期（电脑那边重启过 / 太久没动）」「电脑拒绝了：文件太大」「电脑拒绝了：进度对不上」。
3. **气泡里不放「重试」按钮**——重试是重新走 ① ② 的全新上传，属于文件面板的职责，别让同一条上传出现两个入口。（09-23 曾打算把左侧做成「只放事实、不放动作」，随「不引入左侧」一并作废。）

**预留：方向和类型是两个维度（v2，本文档不设计）**。将来真正的 PC 主动消息（电脑发文件 / 电脑通知）要占左侧，那时会出现**同一个类型在两侧动作相反**的情况（自己发的 `file` 点了是重传，电脑发的 `file` 点了是下载）⇒ 要把「方向」从「类型」里拆成独立字段，且**左侧气泡的动作只能「消费这条消息」**（下载 / 展开），不能「开一个新流程」；点击动作按「方向 × 类型」**查表分派**、查不到就不响应。下载协议不在本文档范围内，真要做时另开一份。

> **什么时候才需要真的加一条下行通知帧**：当出现「**只有服务端知道、而客户端已经不会再发请求**」的事实时。比如用户关掉页面前最后一片落盘失败、或者 TTL 扫描作废了一个会话——这些情况**当前都不需要通知**（没人看了，或者客户端自己知道）。所以 v1 不加；真需要时再加一条 `notice`，并且它必须发**键 + 参数**而不是整句文案（理由同上：语言跟手机走）。

### 5.13 片内进度：为什么必须由 PC 推 【规范】

§5.5 说「用响应里的 `received` 画进度条」，这解决了「估算不准」，但没解决**粒度** —— `received` 只在**整片收完**时回来一次。而在 CF 上，一片 15MB 的实际形态是：

| 阶段 | 客户端看到的 | 真实发生的事 |
|---|---|---|
| 前几秒 | `xhr.upload.onprogress` 冲到 100% | 手机把 15MB 交给了 **CF 的边缘**（CF 先把整个请求体缓冲下来） |
| 之后两三分钟 | **完全静止** | CF 以 ≈100KB/s 回源，PC 在慢慢收 |

⇒ 进度条的真实形态是「几秒满格、然后横住两分钟」，就是 09-23 真机报上来的现象。**根因是 CF 先收后转**：客户端侧的一切估算（`onprogress`、已交给内核的字节数）衡量的都是「字节到 CF 手里了」，而不是「PC 收到了」。

**结论**：片内进度只能由 **PC 自己数的字节**给出，经 WS 下行推给客户端（`upload_progress`，§5.1）。这也把客户端的本地估算整条删掉了 —— 与其让它给出一个方向就错的数，不如不给。

#### 节流：只按恒定 tick 【规范】

09-23 起进度条旁边要显示**最近 10 秒的平均速率**，于是采样必须**规律** ⇒ 节流只剩一个条件：距上次发送 ≥ 100ms（`PROGRESS_TICK = 0.1`）。

| 曾经想过的第二个条件 | 为什么最后没要 |
|---|---|
| 千分位变化（`received * 1000 // size` 变了才发） | 它滤掉噪声的同时，也滤掉了「**没进展**」这件事：慢链路上推进不足一个千分位就不发帧，速率会**冻在旧值**上 —— 看着像还在传，其实早卡住了。速率要的恰恰是这个信号 |

- 只按**大小**（每 N 字节一帧）跨链路不可用：CF ≈100KB/s 与 LAN ≈10MB/s 差 100 倍，同一个固定字节数在 CF 上约 1 秒一帧刚合适，到 LAN 就是**一片 15MB 秒级糊出 100+ 帧**。⇒ 大小只能当附加条件，不能当唯一条件。
- 只按**时间**的代价是慢链路上「帧里没新东西」：CF 下 100ms 只收 10KB，每帧推进 0.02%，肉眼看不见 —— 但那正是速率需要的样本：**有进展是信息，没进展也是信息**。

⇒ 帧率上界 10 帧/秒，帧本身约 60 字节（≈600B/s），走的是 **PC → 手机**方向（被 CF 整形的是手机上行）⇒ 开销可忽略。

#### 速率：最近 10 秒平均，由客户端算 【规范】

进度条下方显示**最近 10 秒的平均速率**；完成气泡里再给一次**全程平均**（总字节 ÷ 从开始到完成的秒数）。两者都**只在客户端算**，帧里不加字段 —— 速率是 `received` 的导数量，属于「怎么画」而不是「发生了什么」。

| 项 | 值 | 理由 |
|---|---|---|
| 窗口 | 10s（`FilePanel.RATE_WINDOW_MS`） | 用户口径；再短会跟着 TCP 抖动一起跳，再长看不出「卡住了」 |
| 补采样节拍 | 1s（`FilePanel.RATE_SAMPLE_MS`） | 节流器是在**读循环**里调的，服务端读不到字节时根本不会发帧 ⇒ 没有补采样，速率就冻在旧值上 |
| 单位 | ≥1MB/s 用 `MB/s`（两位小数）；≥1KB/s 用 `KB/s`；再小用 `B/s` | 跨两个数量级都要能一眼读出来 |

⚠️ 窗口按**真实时间**剪（不是按「最后一个样本的时间」）：卡住时窗口自己往前滑，速率才归零。修剪时保留一个窗口外的锚点，否则 `dt` 会算成 0。

⚠️ 补采样的 `setInterval` **只重画**：不判定成败、不解锁 100%（「界面可以有定时器，不能有权力」），收尾必停。

⚠️ **不需要「收尾强制推一帧」**：收尾由最后一片的 HTTP 响应负责（它带 `received == size`），UI 的 100% 本来就归它解锁（`wire-protocol.md` §9.10 第 5 条）。

#### 实现形状：发送必须串行化 【规范】

进度帧是在 **HTTP handler** 里推的（`_read_upload_body` 的读循环 —— `commit_chunk` 太粗，它是整片一次性 `received += 15MB` 的阶梯），而 WS handler 是**另一个任务**。两者都要经过 `_send_frame`：

```
payload = session.wrap(message)      # 同步：内部 _tx_seq += 1
await websocket.send_bytes(payload)  # ← 让出点
```

`wrap()` 是同步的、不会被打断，所以**两个任务不会拿到同一个 seq**；但 `await send_bytes` 是让出点 ⇒ 两个任务的帧可能**以相反顺序落到线上**，后到的那个反而更早发 ⇒ 接收端直接判重放／解密失败。

⇒ `_send_frame` 用**一把连接级的锁**把「取 seq + 编码」与「发送」包成原子段（`api.py::_send_lock_for`，锁挂在 websocket 对象上）。这是引入第二个发送方**必须**付的成本，不是可选优化。

⚠️ **推帧失败必须静默停发**：连接已关是常态，异常冒到 uvicorn 就是一屏栈（§6.7 第 1 条同族）⇒ 节流器自己 catch 掉并置 `enabled = False`，此后不再尝试。

#### 两条红线 【规范】

1. **只喂 UI，不进状态机**：`upload_progress` 可丢可晚到，「传完了没有」永远由 HTTP 响应回答（`wire-protocol.md` §9.10 第 5 条）。反例就是「进度条 100%、服务端还在等」。
2. **单调**：客户端渲染取 `max(已显示值, 本次值)`。进度帧与 HTTP 响应走两条独立通道，会出现「响应先到、进度帧后到且值更小」的瞬间。

## 6. 实现约束（踩过的和将要踩的坑） 【规范】

### 6.1 拒绝请求时的 RST 坑（最容易翻车的一条） 【规范】

现有的 `_drain_request_body` 是为了修这个：**不读 body 就返回响应**时，若客户端带 `Connection: close`，Windows 会发 RST 而不是 FIN，RST 又会丢弃客户端「已到达但还没读走」的响应 ⇒ 客户端拿到的是 `WinError 10053` 而不是状态码，表现为**概率性失败**。

上传端点的拒绝路径**分两类，排空规则不同**（分类依据见 §5.10「09-20 决定」）：

| 类 | 有哪些 | 要不要排空 |
|---|---|---|
| **拿不出凭证** | MAC 验证失败 / 会话不存在 / 已过期 | **不排空**：不回读 body、直接关连接（RST 无所谓，对面不是自己人） |
| **自己人但状态不对** | 400 / 409 / 413 | **要排空**到「片大小 + 余量」——现有 64KB 上限根本不够，body 有 15MB |

下面几条**只适用于第二类**（需要排空的那一类）：

- **认证 / 校验先于读 body**（不能先收 15MB 再告诉对方「你签名错了」）。验签只需要 HTTP 头（`X-Pm-Mac` + `sid` + `offset` + `len`），所以「拿不出凭证」这一支能在**零 body 字节**时判出来 —— 这正是上表分类可行的前提；
- **排空必须在「返回响应之前」完成**，不能写完响应再排 —— 原因就是上面那条机制：uvicorn 在 `keep_alive=False` 时是**写完响应立刻 `transport.close()`**，等不到我们后面再去读；
- **排空上限按「片大小 + 余量」定，不能留一个小预算**。只读 64KB 然后关连接，剩下的十几 MB 仍然留在接收缓冲里 ⇒ 照样 RST。直觉上「读一点就关能省带宽」在这里是错的：**「关连接时接收缓冲还有未读数据」本身就是 RST 的充要条件**；
- 排空带**单调时钟超时**（几秒）与**字节上限**，两条都触顶就放弃并关闭（此时已是异常客户端，丢一个错误码可以接受）；
- ⚠️ **修正 v2 的一处乐观估计：客户端 `xhr.abort()` 时排空「并不」立刻退出。** 在 CF 下，**CF 会把它手里已收下的字节继续吐完**（它必须把 body 送达才敢收 origin 的响应），所以 origin 侧看到的是**一次正常的读到底**，而不是 `ClientDisconnect`（§5.6.1 主因 1）。⚠️ 但这**不是保证**：CF 还没把 body 收完就被客户端 abort 掉时，它同样会关闭到 origin 的连接，origin 读到的就是 `ClientDisconnect`——2026-09-23 的真机日志（CF 隧道 + 微信内置浏览器）里两种情形都留下了痕迹，所以那一档必须有确定的行为（§6.7）。⇒ 排空在 CF 下是有实际成本的：约十几 MB 的读取，按服务端实测读取速度 15.9MB/s 算约 1 秒。真正「零成本」只出现在**局域网**（TCP 直连时 abort 立刻表现为 `ClientDisconnect`）。另注：取消路径下「读完但不写盘」的形状见 §5.6.3 约束 4；对端**真的**关机（LAN 下 abort）时怎么收尾见 §6.7；
- 逐条补单测（401 / 409 / 413 各一条），与现有 `test_dispatcher.py::test_post_405_drains_body_before_reply` 同形；
- 真机验证一次（§10 阶段 3）——这条坑单测不一定抓得住。

> 换句话说：**对「自己人但状态不对」的请求，也要把 body 传完，这是 HTTP/1.1（在浏览器上）的既定代价。** 换来的是「客户端拿到明确状态码、能对齐后继续」，比省那十几 MB 值。而且这个代价有上限：客户端串行上传 ⇒ **一次会话最多白传一片（§5.10）**。
>
> **对「拿不出凭证」的请求则不排空**（直接关连接）。⚠️ 别把这两类混成一条规则写——早先那句「所有拒绝一律排空」**已作废**，分类规则与理由见 §5.10「09-20 决定」。
>
> 唯一能真正提前叫停 body 的是 `Expect: 100-continue`：**手机端用不了**（JS 设不了这个头、浏览器也不发），但 **`curl` 手工验证时白拿**（uvicorn 只在应用第一次 `receive()` 时才回 `100 Continue`，所以我们的 401 分支不碰 `receive()` 就能让对方一个字节都不发）——细节见 §5.10。

### 6.2 路由与路径放行 【规范】

**第一件：放行 `PUT`。** `api.py` 的 catch-all 路由目前注册的是 `methods=["GET", "HEAD", "POST"]`，不加 `PUT` 的话上传请求会落在**路由层**直接返回 405（不经过 `_dispatch_http`），而且 PUT 是**带 body 的 405** ⇒ 又回到 6.1 那个坑。（`DELETE` 不必放行：取消已改走 WS 帧，见 §5.6.1；万一有人发 `DELETE`，405 的排空由 §6.1 的既有规则覆盖。）

**第二件：`/api/upload/` 要在两种认证模式下都放行**（因为请求不带页面前缀了，§5.2）：

| 模式 | `_normalize_path` 现状 | 要加的东西 |
|---|---|---|
| `url_fragment`（`secret` 非空） | 只认 `/{secret}/…` 前缀，其余一律 404 | 在 **`secret` 分支里**给 `/api/upload/` 开一条前缀放行 |
| `tofu`（`secret` 为空） | 走 `_PUBLIC_PATHS` 的**精确**匹配 | 加一条**前缀**匹配（精确集合里放不下带 `<sid>` 的路径） |

⚠️ **两条分支都要改**，只改一条会在另一种认证方式下静默 404。放行的含义只是「路径能到达 dispatcher」，**不是「谁都能上传」**——门禁是 `k_mac`（§5.3）。这正是 §5.11.5 那条「路径只提供防扫描、不提供授权」的落地。

### 6.3 服务端必须流式写盘 【规范】

用 `async for chunk in request.stream()` 边收边写，**不能 `await request.body()`**（15MB 全进内存，且没有读超时，客户端只声明 `Content-Length` 不发数据就能把 handler 吊住）。另外并发问题：客户端是串行的，但恶意客户端可以并发发两片，需要用一把按 `sid` 的锁保护 `received` 与写句柄。

> 注意：流式解密比流式写盘更难一点——每片是一个完整的 AEAD 密文，必须**整片收齐才能解密**（没有流式 AEAD 接口）。所以实际的形状是「按 `Content-Length` 把本片收进一个 15MB 量级的缓冲 → 解密 → 写盘 → 释放」。也就是说**内存占用 = 片大小**，这正是「片不能无限大」的第二个理由。

### 6.4 客户端必须用 XHR，不能用 fetch 【规范】

| | XHR | fetch |
|---|---|---|
| 上传进度 | `upload.onprogress` | 需要 `duplex: "half"` + ReadableStream |
| Safari / iOS / 微信内置浏览器 | ✅ | ❌ **不支持**，而手机正是主平台 |
| 取消 | `abort()` | `AbortController` |

选 XHR 的理由现在只剩**兼容性**与**取消语义**两条：进度已经不吃 `upload.onprogress` 了（§5.13 改由 PC 推），所以「fetch 拿不到上传进度」不再成立；但「Safari／微信内置浏览器不支持 `duplex`」与「`abort()` 更直接」仍然成立。

> **保留一段历史坑**：iOS 18 的 WebKit 有个已知 bug（#277286），XHR `upload.onprogress` 里的 `event.total` 在**上传完成前是错的**（会给出 2⁶⁴ 量级的值）。当时的绕过办法是「分母用自己算的长度，不信 `event.total`」。改由服务端给进度后这条约束**整条消失**（那个事件已经不读了），但**别再把本地估算加回来** —— 它在 CF 下的错误不是精度问题，是方向问题（§5.13）。

### 6.5 上传期间的 WS 保活 【规范】

服务端判活的依据是「有没有收到任何 WS 消息」（45s 发 ping / 60s 判死）。**HTTP 上传不刷新这个时间戳**——上行被传满时，`pong` 排在数据后面回不来，一条健康的上传有可能在 60s 时被服务端判死（15MB 的大片在慢上行上更容易超过这个窗口）。

处理方式二选一——⚠️ **09-23 之后这条从「建议修」升级成「必做」**：WS 判死的后果已经不是「UI 显示离线」，而是**正在传的上传被直接取消**（§5.6.4）⇒ **一条健康的、跑在 CF 上的大文件上传会在 60 秒时把自己杀掉**。

1. **让 HTTP 活动也刷新对应连接的心跳时间戳**（会话表里存会话所属的 WS 连接引用，PUT 命中时刷新 `last_msg_ts`）——**采用**；
2. （备选）存在活跃上传会话时，暂时不判死。

> 判活依据仍然是 `_ConnectionLiveness.last_msg_ts`（**不是 pong**），`_KEEPALIVE_TIMEOUT`(60s) 必须 < CF idle(~100s)（`wire-protocol.md` §7）。

### 6.6 并发上传 【规范】

v1 建议**客户端串行**（同一时刻只传一个文件），服务端按 `sid` 天然支持多路但不做队列。这样「单会话单文件」的约束从服务端下移到客户端，服务端不必维护互斥。

> 顺带说明：**不做片级并发**。按 §1.2 的算式，15MB 一片已经让 RTT 部分可以忽略，串行足以跑满手机上行；而片级并发会让片乱序到达，把 §5.5 的三行判定扩充成「乱序窗口 + 缺口补齐」，复杂度陡增而收益有限。将来真要提速，先看手机上行是不是已经跑满。

### 6.7 对端半路断开（`ClientDisconnect`） 【规范】

§6.1 最后一条的反面：局域网下客户端 `xhr.abort()`（或者页面被切走）会**立刻**表现为对端关机，`request.stream()` 抛 `starlette.requests.ClientDisconnect`。这一档**不属于**「要排空的那一类」——**没有字节可等了**，连接已经死掉，排空无从谈起。

三条规则：

1. **不许冒到 uvicorn。** 漏接的后果是 `Exception in ASGI application` 加一整屏栈，看起来像服务端崩了（与握手收尾那条同族，见 `api.py::_try_send_bytes`）。三条读 body 的路径各自接住（`_drain_request_body` / `_read_upload_body` / `_receive_client_log`），另在 `app` 上注册 `ClientDisconnect` 异常处理器**兜底**——将来新写的读 body 代码忘了接，也只回一个 4xx，不出栈。
2. **绝不能把半截密文交出去。** 实收字节少于声明长度时若照常 `commit_chunk`，解密必然失败，日志上记成 `reason=decrypt:` ⇒ 把「客户端走了」伪装成「解密失败」，属于最容易带偏排查方向的一类假信号。⇒ `_read_upload_body` 用 `None` 表示「对端走了」，调用方**直接收工：不解密、不 commit**。
3. **不作废会话。** 谁走的就让谁去清理：取消走 WS 的 `upload_cancel`、断连走 `abort_for_conn`、都没有就等 TTL。HTTP 层因为「对端走了」就 `abort_session`，等于凭空多出一条协议外的作废路径，而且它**区分不出「用户取消」与「网络抖了一下」**。会话也挂不久：客户端一旦中止就会跟一发 `upload_cancel`，不存在挂着等 TTL 的实际风险。

> ⚠️ 这一档**可能读不到响应**：uvicorn 收到 EOF 后会自己关掉传输，响应写不出去。⇒ 用例别断言状态码（`tests/test_upload.py::_raw_truncated` 的 docstring 写了原因），要断言的是**会话状态没变**。
